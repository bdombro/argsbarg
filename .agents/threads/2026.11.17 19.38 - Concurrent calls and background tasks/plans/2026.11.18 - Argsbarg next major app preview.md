# Argsbarg next major: app preview

Disposition: superseded by the released v9 API and current examples. This preview remains as
design provenance and is not an executable compatibility target.

`myreports` generates the same report from a CLI command, a REST route, or an MCP tool. This is a walkthrough of one draft API, not code that runs with the current package. The [design decisions](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md) are the source of truth.

- **Assumption** means this walkthrough picks a tentative API so the example can continue.
- **Blocked** means the example stops at a missing contract instead of inventing an API.

## What users do

| Surface | Generate a report for project `alpha` |
| --- | --- |
| CLI | `myreports report alpha` |
| REST | `POST /api/projects/alpha/reports` |
| MCP | `tools/call` with `name: "generate_report"` and `arguments: { projectId: "alpha" }` |
| Local mirrors | `myreports api POST /api/projects/alpha/reports` or `myreports mcp call generate_report` with `{"projectId":"alpha"}` on stdin for the tool |

These are launch or call examples for the same executable. The CLI and local mirrors don't start a server. MCP uses the same tool over stdio and Streamable HTTP. Apps that want JSON-RPC 2.0 declare a separate optional `jsonRpc` surface (with `/rpc`, `/rpc/openrpc.json`, and `myreports rpc ...`) instead of auto-generating RPC from HTTP routes.

With [`--relay`](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#73-in-process-cli-mirrors), the CLI can call a running server instead: `myreports mcp call generate_report --relay https://reports.example/mcp` reads the same tool arguments from stdin and sends a real MCP HTTP request. The server's `/mcp` middleware and guards apply.

## Declare the app

**Selected app model — [7.1, Approach C: use a surface-neutral factory](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#approach-c-use-a-surface-neutral-factory).** This draft uses one factory with separate `cli`, `http`, and `mcp` blocks (and optional `jsonRpc` when needed). The exact API is still illustrative. App code supplies a lazy, borrowed `reports` repository; building the app doesn't connect to a database. `generateReport` and `verifyReporter` are app code, not framework helpers.

`myreports` declares all three blocks below to demonstrate bespoke CLI, REST, and MCP declarations side by side. Many apps don't need all three: declaring only the REST route already gives REST, OpenAPI, and the `myreports api ...` CLI mirror; declaring only the MCP tool already gives stdio, Streamable HTTP, and `myreports mcp call ...`. Add a bespoke CLI command (or another surface) only when that surface needs tailored ergonomics or a different contract.

```typescript
import { argsbarg, command, OptionKind } from "argsbarg";
import { z } from "zod";

const Project = z.object({ projectId: z.string().min(1) });
const Report = z.object({ projectId: z.string(), total: z.number() });

function buildApp(reports: ReportRepository) {
  const report = (projectId: string, caller: Reporter, signal: AbortSignal) =>
    generateReport({ reports, projectId, caller, signal });

  return argsbarg({
    key: "myreports",
    description: "Generate project reports.",
    version: "1.0.0",
    cli: {
      commands: [
        command({
          key: "report",
          description: "Generate a project report.",
          positionals: [{
            name: "projectId", kind: OptionKind.String, description: "Project ID.",
          }],
          inputSchema: Project,
          outputSchema: Report,
          guard: requireReporter,
          handler: ({ inputs, locals, signal }) =>
            report(inputs.projectId, locals.caller, signal),
        }),
      ],
    },
    http: {
      routes: [{
        method: "POST",
        path: "/projects/:projectId/reports",
        pathParams: Project,
        outputSchema: Report,
        guard: requireReporter,
        handler: ({ inputs, locals, signal }) =>
          report(inputs.projectId, locals.caller, signal),
      }],
    },
    mcp: {
      stdio: true,
      http: true,
      tools: [{
        name: "generate_report",
        description: "Generate a project report.",
        inputSchema: Project,
        outputSchema: Report,
        guard: requireReporter,
        handler: ({ inputs, locals, signal }) =>
          report(inputs.projectId, locals.caller, signal),
      }],
    },
    server: { listeners: () => readListeners(process.env) },
  });
}
```

Argsbarg adds the REST `/api` prefix. `Project` and `Report` happen to fit multiple surfaces in this app; authors can use different schemas where those contracts differ. To also expose JSON-RPC 2.0 methods (with `/rpc/openrpc.json` and `myreports rpc ...`), add a sibling `jsonRpc` block rather than mirroring HTTP routes. The MCP client discovers the tool through `tools/list`.

**Selected behavior — [7.16, Option A: native binding and shared invocation](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#option-a-native-binding-shared-guarded-invocation).** The route declares `projectId` as a path parameter and exposes it in `inputs`, just like the command and tool. Declared query and body fields join it in the same object without overlapping keys.

## Guard a call

**Selected behavior — [7.1: guard and context API](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#per-call-context-and-guard-results).** `source` describes how the call arrived, so an `api` CLI mirror is local even though it calls a route. The type and helper signatures below are illustrative.

```typescript
type CredentialSource =
  | { source: "local"; env: { get(name: string): string | undefined } }
  | { source: "http"; headers: { get(name: string): string | undefined } };

async function requireReporter(ctx: CredentialSource) {
  const raw = ctx.source === "http"
    ? /^Bearer (.+)$/i.exec(ctx.headers.get("Authorization") ?? "")?.[1]
    : ctx.env.get("REPORT_TOKEN");
  const caller = raw ? await verifyReporter(raw) : undefined;

  if (!caller) {
    return deny("Reporter credential required", {
      httpStatus: 401,
      headers: { "WWW-Authenticate": "Bearer" },
    });
  }
  return allow({ caller });
}
```

HTTP reads request headers, including over a Unix socket. CLI and MCP stdio read process env. A missing HTTP credential can't fall back to `REPORT_TOKEN`. REST can render the app's HTTP denial; CLI, MCP, and individual RPC operations render their own denial without changing the outcome of another call. Handlers receive the verified caller, not a raw credential; concurrent calls never share caller state.

This sketch uses an app token, not hosted OAuth. The selected [opt-in `/mcp` OAuth helper](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#721-oauth-for-mcp-over-http) would verify incoming OAuth tokens through an app-supplied verifier before tool dispatch. Without `--relay`, `myreports mcp call` runs the surface and tool guards, not the HTTP OAuth middleware. A protected tool still requires a verified caller on the local path.

## Start the same executable

**Selected convention — [7.11: launch commands](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#711-startup-commands-and-distribution) and [7.1: listener config](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#listener-shape-and-endpoint-reachability).** When any service surface (`http`, `jsonRpc`, or `mcp`) is configured, `serve` is the standard first positional command (`myreports serve ...`) that enters long-lived service mode and stays running until shutdown (`SIGINT`/`SIGTERM`). Packaging supplies the same executable path with stdio launch arguments (`serve mcp --stdio`).

The app makes both MCP modes available, but each launch starts only one. Run the stdio and HTTP commands in separate processes if you want both running at once. The HTTP process can serve REST and `/mcp` on the same listener.

```sh
myreports --help
myreports report alpha
myreports serve mcp --stdio

myreports serve http
# In a second terminal:
curl http://127.0.0.1:3000/health/readiness
curl -X POST -H "Authorization: Bearer $REPORT_TOKEN" \
  http://127.0.0.1:3000/api/projects/alpha/reports
```

HTTP mode is the only mode that calls `readListeners`. This app-owned Zod adapter chooses which binds to use; neither argsbarg nor a request header interprets these variable names. An explicit socket-only result never opens a TCP port.

```typescript
function readListeners(env: NodeJS.ProcessEnv) {
  const mode = z.enum(["tcp", "socket", "both"]).default("tcp").parse(env.MYAPP_LISTEN);
  const socket = () => ({
    path: z.string().trim().min(1).parse(env.MYAPP_SOCKET_PATH),
  });
  if (mode === "socket") return { socket: socket() };

  const tcp = {
    host: z.string().min(1).default("127.0.0.1").parse(env.MYAPP_HOST),
    port: z.coerce.number().int().min(1).max(65535).default(3000).parse(env.MYAPP_PORT),
  };
  return mode === "both" ? { tcp, socket: socket() } : { tcp };
}
```

```sh
# Start with ./run already present and restricted to the intended local users.
MYAPP_LISTEN=socket MYAPP_SOCKET_PATH=./run/myreports.sock myreports serve http
# In a second terminal:
curl --unix-socket ./run/myreports.sock http://localhost/health/readiness
```

With `MYAPP_LISTEN=both`, TCP and the socket serve the same enabled routes and guards. An invalid port or missing required path fails HTTP startup without affecting `--help` or stdio. Stdio keeps its protocol on stdout; the client needs Unix socket support or a proxy to use `/mcp` over the socket.

**Blocked — [7.1: startup and shutdown ownership](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#start-inspect-and-close).** `app.run()` now commits to setting `process.exitCode` (or returning an exit code) and resolving normally rather than calling `process.exit()`, so app-owned `try { await app.run(); } finally { await reports.close(); }` cleanup reliably runs. The preview still stops short of finalizing how callers inspect bound `addresses` (e.g., ephemeral port `0`) or whether a lower-level `app.startHttp()` / `app.serve()` handle is exposed alongside `app.run()`. On failure it must release any partial bind. On shutdown it must stop or drain its calls before the app closes the repository; closing the server alone must not dispose of a borrowed repository.

## Add a long-running export

The synchronous `generate_report` tool above needs no task provider. A separate `export_report` could enqueue work in the app's durable queue and return a task reference when a capable client requests task execution. A caller then uses `tasks/get` to read status and the terminal result, and `tasks/cancel` where supported. The provider verifies task ownership on every operation. Disconnecting from HTTP or stdio doesn't cancel the durable export.

**Blocked — [7.20: provider signatures](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#720-app-supplied-task-provider) and [7.1: caller context](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#per-call-context-and-guard-results).** The named `get`, `update`, and `cancel` callbacks and explicit task return are selected. The preview still needs the exact registration and return signatures and the verified caller handoff. The app owns the queue, retries, and reporting.
