# Argsbarg next major: design decisions

Disposition: implemented by the v9 implementation plan and released as `argsbarg@9.0.0`.
Task 39 was replaced by task 39.1; task 78 was dropped when narrower review tasks superseded it.
MCP Tasks, hosted OAuth, browser upstream sign-in and real-host compatibility remain explicitly
deferred or unverified in the release docs and task evidence.

Argsbarg should keep a small CLI simple and let a larger app declare each operation on the surface that fits best while getting its local CLI mirror for free — all in one zero-dependency, Zod-native runtime with unified guards, invocation isolation, streaming, and single-executable packaging. Apps choose any combination of independent optional surfaces: `cli`, `http` (REST + OpenAPI + `myapp api ...`), `jsonRpc` (JSON-RPC 2.0 + OpenRPC + `myapp rpc ...`), and `mcp` (stdio + Streamable HTTP `/mcp` + `myapp mcp call ...`). Authors only write bespoke declarations on multiple surfaces when each surface needs its own ergonomics or wire contract, without routing network calls through argv or auto-generating cross-protocol HTTP/RPC endpoints. The existing factory, CLI-as-core model, and public API are candidates, not starting constraints.

This is a breaking major: [backward compatibility and a migration path are non-goals](#712-breaking-major-without-an-8x-migration-path). The current distribution choices are [one npm package](#710-package-and-repository-placement) and [one executable per app](#711-startup-commands-and-distribution); neither dictates the declaration or runtime model.

This document records design choices and the behavior they need to support. Once the design is settled, write a separate implementation plan for the selected design. The [earlier experiment record](./2026.11.17%20-%20Concurrent%20calls%20and%20background%20tasks.md) is evidence, not a plan to ship three libraries.

The [app preview](./2026.11.18%20-%20Argsbarg%20next%20major%20app%20preview.md) shows one reporting app built around the current proposals and marks where open decisions interrupt the walkthrough.

The [use-case guides](../../../../docs/use-cases/README.md) own the scenarios and walkthroughs. They separate released 8.x support, next-major previews, app-owned integrations, and intentional exclusions.

## Design decisions

Each decision has its own status. ✅ means the choice is settled, not implemented; ❓ means the choice is still open. Previews show what an app author or caller would see. Proposed code, file trees, package names, and launch commands are illustrative, not API or layout commitments.

Decision numbers are retained from the earlier plan for discussion. Former 7.2 and the API choices it absorbed (7.14, 7.15, 7.17, and 7.18) now live in 7.1.

### 7.1. App model, composition, and lifecycle

Status: ✅ Approach C selected. ❓ [API details remain open](#open-api-choices).

**Decision.** Use [Approach C, the surface-neutral factory](#approach-c-use-a-surface-neutral-factory). Preserve `argsbarg(spec)` and `app.run()`, with independent optional `cli`, `http`, `jsonRpc`, and `mcp` blocks. Declare each operation on the surface whose contract fits best — relying on in-process CLI mirrors (`myapp api ...`, `myapp rpc ...`, `myapp mcp call ...`) instead of duplicating declarations — and add bespoke declarations on additional surfaces only when those surfaces need distinct names, inputs, or ergonomics, sharing business logic in ordinary app code. Each surface accepts an optional default `guard` that individual operations can supplement or override. This keeps small CLIs simple and allows wire-specific inputs and outputs without coupling REST, JSON-RPC, and MCP to one another. D's required operation layer adds indirection even to single-surface apps; E puts more startup wiring on every app author. Their sketches are retained for comparison.

A report can be the same operation across three surfaces without taking the same wire inputs or having the same public name. The sketches compare what authors declare, who launches the executable, and who closes its resources. The selected design must meet the [startup requirements](#packaging-and-startup), [invocation and guard rules](#invocation-context-and-guards), and [verification scenarios](#verification-examples).

**Context.** Argsbarg 8.x derives HTTP routes and MCP tools from the CLI tree and converts their requests back to argv. The next major can instead bind inputs at each surface and share the invocation logic. [Packaging stays one package](#710-package-and-repository-placement); that leaves the app's public API open.

#### Approaches at a glance

| End-to-end approach | Small `greet` CLI | MCP-only app | Stateful `myreports` |
| --- | --- | --- | --- |
| [C. Use a surface-neutral factory](#approach-c-use-a-surface-neutral-factory) | Put `greet` under `cli.commands` and call `app.run()`. | Declare only `mcp`; no CLI block or dummy command. | Put each declaration under its surface. The factory assembles the executable and the app owns the repository. |
| [D. Define operations first](#approach-d-define-operations-first) | Define a `greet` operation and bind it to a command. | Bind an operation to a tool and let the facade launch stdio without an HTTP listener. | Bind CLI, REST, and MCP to one report operation. Compare the shared schema and policy against the extra binding layer. |
| [E. Compose surfaces independently](#approach-e-compose-surfaces-independently) | Run just the command module. | Start the MCP module directly on stdio. | Assemble all three surfaces with one HTTP dispatcher. The executable selects the mode and owns acquisition and shutdown order. |

The three `myreports` sketches expose `myreports report alpha`, `POST /api/projects/alpha/reports`, and the `generate_report` tool with `{ "projectId": "alpha" }`. They share the `requireReporter` guard and report logic below. In each sketch the app owns a lazy repository, so configuring the app and asking for help don't open a database connection. All function names and signatures are illustrative.

```typescript
const Project = z.object({ projectId: z.string().min(1) });
const Report = z.object({ projectId: z.string(), total: z.number() });

const reportWith = (reports: ReportRepository) =>
  (projectId: string, caller: Reporter, signal: AbortSignal) =>
    generateReport({ reports, projectId, caller, signal });
```

For the [curated gateway](../../../../docs/use-cases/gateway.md), C passes app-built declarations into the factory, D binds them to operations, and E assembles them in each surface module. Verify that C can build a catalog at startup, attach policy to entries, and invoke an app-owned client or task provider using public APIs only.

#### Approach C: Use a surface-neutral factory

Keep `argsbarg(spec)` and `app.run()` from 8.x. Put each surface in its own optional block and replace command-derived exposure with explicit routes and tools. Each declaration binds its own inputs and calls the same report function.

```typescript
const reports = lazyReportRepository();
const runReport = reportWith(reports);
const app = argsbarg({
  ...metadata,
  server: { listeners: () => readListeners(process.env) },
  cli: {
    commands: [command({
      key: "report",
      positionals: [{ name: "projectId", kind: OptionKind.String }],
      inputSchema: Project,
      outputSchema: Report,
      guard: requireReporter,
      handler: ({ inputs, locals, signal }) =>
        runReport(inputs.projectId, locals.caller, signal),
    })],
  },
  http: {
    routes: [{
      method: "POST",
      path: "/projects/:id/reports",
      pathParams: z.object({ id: Project.shape.projectId }),
      outputSchema: Report,
      guard: requireReporter,
      handler: ({ inputs, locals, signal }) =>
        runReport(inputs.id, locals.caller, signal),
    }],
  },
  mcp: {
    stdio: true,
    http: true,
    tools: [{
      name: "generate_report",
      description: "Generate a project report.",
      inputSchema: Project,
      outputSchema: Report,
      guard: requireReporter,
      handler: ({ inputs, locals, signal }) =>
        runReport(inputs.projectId, locals.caller, signal),
    }],
  },
});

try {
  await app.run();
} finally {
  await reports.close();
}
```

The smallest CLI adds a level of nesting: `argsbarg({ ...metadata, cli: { commands: [greet] } }).run()`. An MCP-only app doesn't need a CLI block. The factory selects the mode, resolves listeners only for HTTP, and closes its transports before returning control to the executable. The app closes the repository. An in-process caller can supply a fake repository and use `app.invoke()` without opening a listener.

C can [mount standalone app definitions](../../../../docs/use-cases/child-apps.md) by key. The key sets the public namespace. A keyed descriptor leaves room for explicit mount policy without requiring an option per credential.

#### Approach D: Define operations first

Define domain input, a handler, and policy once where the operation really is shared. Each surface chooses which operations to expose and maps its native input into that schema. A CLI-only `greet` now needs an operation and a CLI binding; a reporting app can validate the domain input and enforce common policy in one place. The downside is a second layer even for single-surface commands and routes, plus pressure to force a shared result schema onto wire-specific responses such as HTTP downloads.

```typescript
const reports = lazyReportRepository();
const runReport = reportWith(reports);
const report = operation({
  input: Project,
  output: Report,
  guard: requireReporter,
  handler: ({ input, locals, signal }) =>
    runReport(input.projectId, locals.caller, signal),
});

const reportCommand = command("report", report, {
  projectId: positional("projectId"),
});
const reportRoute = route("POST /projects/:id/reports", report, {
  projectId: param("id"),
});
const reportTool = tool("generate_report", report);

const app = argsbarg({
  ...metadata,
  server: { listeners: () => readListeners(process.env) },
  cli: { commands: [reportCommand] },
  http: { routes: [reportRoute] },
  mcp: { stdio: true, http: true, tools: [reportTool] },
});

try {
  await app.run();
} finally {
  await reports.close();
}
```

The route maps `id` to `projectId`; the tool uses the operation's input names as-is. The bindings have no separate report handler or guard. For MCP-only, keep just the tool binding and select stdio. The factory owns transport startup and shutdown as in C; the operation borrows the repository and the app closes it. The comparison with C is about what authors declare, not how the server starts.

#### Approach E: Compose surfaces independently

A CLI-only app runs `runCli([greet])`; an MCP-only app passes its tool registry to `startMcpStdio`. For reporting, the executable composes CLI, REST, and MCP modules from the same package and passes each only the dependencies it needs. The modules can share validation and invocation, a reports repository, and one HTTP dispatcher. The app chooses which surface to start; this fits embedders and MCP-only apps well, but puts more work on authors to wire launch modes, local mirrors, and cleanup.

```typescript
const reports = lazyReportRepository();
const runReport = reportWith(reports);
const cli = defineCli([command({
  key: "report",
  positionals: [{ name: "projectId", kind: OptionKind.String }],
  inputSchema: Project,
  outputSchema: Report,
  guard: requireReporter,
  handler: ({ inputs, locals, signal }) =>
    runReport(inputs.projectId, locals.caller, signal),
})]);

const rest = defineRoutes([{
  method: "POST",
  path: "/projects/:id/reports",
  pathParams: z.object({ id: Project.shape.projectId }),
  outputSchema: Report,
  guard: requireReporter,
  handler: ({ pathParams, locals, signal }) =>
    runReport(pathParams.id, locals.caller, signal),
}]);

const mcp = defineMcp([{
  name: "generate_report",
  description: "Generate a project report.",
  inputSchema: Project,
  outputSchema: Report,
  guard: requireReporter,
  handler: ({ inputs, locals, signal }) =>
    runReport(inputs.projectId, locals.caller, signal),
}]);

try {
  await runExecutable({
    cli,
    serveHttp: async () => {
      const running = await startHttp({
        routes: rest, mcp, listeners: readListeners(process.env),
      });
      try {
        console.log(running.addresses);
        await waitForShutdownSignal();
      } finally {
        await running.close();
      }
    },
    serveStdio: () => startMcpStdio(mcp),
  });
} finally {
  await reports.close();
}
```

The executable controls launch and cleanup. Only the HTTP branch reads listener settings. It closes the server before closing the repository, including when waiting for shutdown fails. If binding fails before a handle is returned, `startHttp` cleans up any partial binds and the executable still closes the repository. This ownership is useful for embedders; it costs more launch code in a stock app.

#### Open API choices

The exact child-mount API is open. [Shared invocation](#716-input-binding-and-shared-invocation), [MCP transport adapters](#719-mcp-transport-adapters), and [the task-provider contract](#720-app-supplied-task-provider) remain separate decisions.

##### Per-call context and guard results

**Settled context and guard results.** `ctx.inputs` holds all validated operation inputs, including CLI flags and positionals. Narrow on `ctx.source`: `"local"` (CLI, local mirrors, or MCP stdio) exposes `ctx.env.get(name)`; `"http"` exposes `ctx.headers.get(name)` with case-insensitive header lookup. Neither accessor reads from the other source. App startup configuration is separate from call context.

Guards are callbacks, synchronous or async. `true` allows without adding `locals`; `false` denies with a default diagnostic. Use `allow({ caller })` or equivalent to pass verified data without mutating context, and `deny(...)` for specific reasons or challenges. A handler can rely on a required `locals.caller` only if every enabled path that reaches it establishes one.

Each surface (`cli`, `http`, `jsonRpc`, `mcp`) accepts an optional default `guard`; per-operation guards can supplement it (running after the default and receiving its `locals`) or explicitly replace it. Replacing the default does not disable transport or mount checks. The exact override syntax, TypeScript composition, and structured denial fields remain open (see the [guard composition note](./2026.11.19%20-%20Guard%20composition%20and%20caller%20handoff.md)).

##### Listener shape and endpoint reachability

Prefer typed, keyed `server.listeners` over separate flags or an array that needs duplicate checks. The proposal is loopback TCP at `127.0.0.1:3000` when omitted; explicit `tcp` and `socket` keys replace that default set, `{ tcp: {} }` uses TCP defaults, and an empty set is invalid. If both are enabled, use the same dispatcher rather than giving each bind a different set of routes. Prefer app-owned Zod env parsing over framework env names and precedence rules. A factory can accept the illustrated lazy resolver; an explicit launcher can pass the resolved object. If launch flags are useful, normalize them to the same config.

##### Start, inspect, and close

When any service surface (`http`, `jsonRpc`, or `mcp`) is configured, `serve` is the standard first positional command (`{app} serve ...`) that starts long-lived service mode and stays running until shutdown (`SIGINT`/`SIGTERM`). `app.run()` sets `process.exitCode` (or returns an exit code) and resolves normally instead of calling `process.exit()`. That guarantees app-owned `try { await app.run(); } finally { await reports.close(); }` cleanup actually runs after CLI commands, local mirrors, and graceful server shutdown.

Prefer a running handle with actual `addresses` (including an OS-assigned port) and `close()` over a restartable class for tests and embedders (`app.startHttp()` or similar). Still decide the exact programmatic handle signature alongside `app.run()`. The sketches borrow state through closures. Consider an opt-in `state.open()` returning `{ value, close }` only if apps repeatedly write the same lifecycle code; it would need rules for one-shot invocations and concurrent initialization. Shared dependencies can go in `appState` if that option wins; caller identity stays per call. A general plugin lifecycle would also need ordering and rollback rules, and none of these examples requires one.

### 7.3. In-process CLI mirrors

Status: ✅

An app author should be able to exercise a declared route, method, or tool from a terminal without maintaining its CLI equivalent or starting a server locally.

**Context.** Sending the same request over a socket is useful for testing transport behavior. For local invocation, the dispatcher already lives in the process. Repeating the operation as an independent CLI command risks changing validation or access rules in only one place.

**Local by default.** Generated CLI mirrors use the same local dispatch, validation, and operation-side guards. `myapp api GET /health/readiness` uses the full path with no `/api` inference. `myapp mcp call` runs `mcp.guard` and the selected tool's guard according to the same composition rules as a wire call. Local calls use CLI env context and don't run HTTP middleware or construct a synthetic request. Put policy that must apply on both paths in a shared guard; the guard and middleware can reuse the same app-owned verifier.

**Opt-in network relay.** Add `--relay <url>` to the generated `api`, `rpc`, and `mcp call` commands. With the flag, the CLI sends a real request to an already-running server using the surface's native wire protocol. It does not invoke a local handler or start a listener. The destination server applies its own middleware, validation, and guards. Do not copy the CLI environment into request headers or fall back to local execution if the remote call fails. Exact credential and response-display options remain open.

Illustrative syntax: REST combines the relay origin with the explicit request path; RPC and MCP use the supplied endpoint URL.

```sh
myapp api POST /api/reports --relay https://reports.example < report.json
myapp rpc reports.generate --relay https://reports.example/rpc < report.json
myapp mcp call generate_report --relay https://reports.example/mcp < report.json
```

MCP relay sends a `tools/call` request over Streamable HTTP to `/mcp`; it doesn't require a separate endpoint that publishes tools as top-level JSON-RPC methods.

### 7.4. Stream responses and isolate concurrent calls

Status: ✅

An operation can stay open while it produces output, and a second operation may need to run before the first can finish. The framework should support both without owning long-lived work.

**Context.** Argsbarg's concurrency work already isolates captured output per invocation. That addresses overlapping handlers and MCP stdout, not whether an agent host can wake an idle session. HTTP streams similarly have a transport lifetime that may differ from the lifetime of an app's job.

**Options and previews.** Buffering a report download or NDJSON feed produces one ordinary response but delays the first byte and uses memory for the entire result. A streamed response can deliver the first chunk immediately and stop when its reader disconnects. WebSockets and streaming uploads add more protocol and lifecycle handling than those examples need. Serializing tool calls protects process-global output, but a pending `wait` would then block the call that sends the answer. Concurrent invocation scopes allow both calls without mixing their outputs.

**Decision.** Support streamed response bodies, backpressure, and disconnect handling. Calls can overlap asynchronously by default, including MCP calls on the same connection, without a concurrency opt-in. An awaiting `wait` must not hold up the call that unblocks it. Keep output, caller context, and cancellation isolated per invocation; preserve wire framing without serializing handler execution. Synchronous JavaScript still blocks the process, and apps own synchronization of shared state. Defer broader stream protocols. A disconnect ends the response, not an app-owned durable job. Keep swarm-mode's background shell wait for waking an idle agent; overlapping MCP calls do not provide that host behavior.

### 7.5. Standalone JSON-RPC surface

Status: ✅

JSON-RPC 2.0 should be its own optional surface (`jsonRpc`), not auto-generated from HTTP REST routes. Likewise, MCP tools keep their MCP JSON-RPC wire protocol without auto-generating plain HTTP endpoints (`/tools/{name}`).

**Context.** Earlier drafts tried to auto-generate `/api-rpc` from HTTP REST routes and `/tools/{name}` from MCP tools. Auto-generating RPC from HTTP routes leaked REST mechanics (verb-and-template method names like `GET /api/reports/:id`, nested `params.path` vs flat inputs, stream/status-code exclusion rules) into JSON-RPC, while auto-generating plain HTTP from MCP tools blurred MCP's protocol/auth boundary with REST.

**Decision.** Provide a separate optional `jsonRpc` surface alongside `cli`, `http`, and `mcp`. Apps declare JSON-RPC methods explicitly with their own names, Zod `inputSchema` / `outputSchema`, and guards, sharing business logic in ordinary app code. Do not auto-generate JSON-RPC endpoints from `http` routes, and do not auto-generate plain HTTP `/tools/{name}` endpoints from `mcp` tools. MCP keeps its own JSON-RPC protocol over stdio and Streamable HTTP `/mcp`. The `jsonRpc` surface serves JSON-RPC 2.0 (including batches) on the shared HTTP server (e.g., `POST /rpc`), publishes OpenRPC discovery (`/rpc/openrpc.json`), and gets an in-process CLI mirror (`myapp rpc <method>`).

**Discarded: `/mcp-rpc`.** Do not expose MCP tools as top-level JSON-RPC methods on a separate endpoint. MCP clients and `mcp call --relay` use `tools/call` on `/mcp`. Apps that want to offer the same operation to plain JSON-RPC clients can declare it explicitly under `jsonRpc`.

### 7.6. Discovery matches callable operations

Status: ✅

Generate discovery from the same definitions as dispatch, for the operations registered on each surface. This also applies to [gateway declarations](../../../../docs/use-cases/gateway.md#publish-your-contract-not-the-upstream-catalog); guards still authorize individual calls.

**Context.** OpenAPI describes HTTP paths and verbs; OpenRPC describes JSON-RPC method names and params. MCP has its own discovery: tools are named arguments to `tools/call`, not standalone wire methods.

**Decision.** Keep `/api/openapi.json` (and `/api/docs`) for `http` REST routes, `/rpc/openrpc.json` for the standalone `jsonRpc` surface, and `server/discover` + `tools/list` for `mcp`. Skip `/mcp/openrpc.json` (tools are arguments to `tools/call`, not standalone RPC methods) and drop `/tools/openapi.json` along with the removed plain HTTP tool mirror.

### 7.7. One MCP plugin with two transports

Status: ✅

Transport choice should be a deployment decision, not a second set of MCP tools to author.

**Context.** Stdio and Streamable HTTP differ in framing, request context, and lifecycle. They share schemas, tool dispatch, capabilities, and the MCP revision. The REST and JSON-RPC surfaces don't own any of those.

**Options and previews.** Separate transport plugins might isolate dependencies, but an app serving `generate_report` locally and at `/mcp` would need to coordinate two configurations and their capabilities. With one plugin, a desktop agent can launch a stdio process while a separately launched HTTP process serves other agents on the same machine. They can share app-owned storage, but not process memory.

**Decision.** Use one tool declaration type and one registry for stdio and Streamable HTTP. An app can make both launch modes available, but a process runs only the transport selected at launch. Simultaneous stdio and HTTP MCP in one process is intentionally unsupported. MCP HTTP can share the HTTP server with REST and/or JSON-RPC or run without them.

### 7.8. MCP task protocol in the plugin, task execution in the app

Status: ✅

MCP needs a way to refer to work that hasn't finished. It doesn't require argsbarg to start, store, or schedule that work.

**Context.** Earlier designs addressed both a slow handler that outlives its caller and durable jobs that wait for an available worker. Those have different failure modes. Persisting a live handler's status doesn't make the handler resumable after a crash, and queue deduplication doesn't make external side effects exactly once.

**Timed promotion preview.** A tool sets `promoteAfter`, runs inline initially, and returns a task reference if the threshold expires. The prototype's SQLite store holds references and results. This is easy for an app author, but makes argsbarg responsible for lease recovery, expiry, cancellation, and process lifetime.

**Queue previews.** The lite option gives an `emails` worker atomic claims, leases, delay, and attempts; app code adds retry and scheduling policy. A custom worker could find a candidate and then try to claim it atomically. The config-first option adds built-in priority, bounded retry, cron, and failed-job replay, making jobs such as email, webhooks, and nightly syncs low-code. Both still leave the framework maintaining delivery and storage semantics; neither guarantees a good fit for transactional enqueue, per-tenant fairness, or an app that already uses a queue.

**Provider preview.** `tools/call` returns a task reference from the app. A capable client follows it with `tasks/get`; the plugin validates the message and dispatches to the provider with caller context. An in-process export can keep state in memory, while another app maps the reference to a job in its existing durable queue. Neither writes its own JSON-RPC or takes a storage dependency from argsbarg.

Illustrative tool and `tasks/get` provider callback. `reportJobs` is app-owned; a client without task support takes the inline path before anything is enqueued.

```typescript
async function reportTool(ctx) {
  if (!ctx.supportsTasks) return generateReport(ctx.inputs);

  const job = await reportJobs.enqueue(ctx.inputs, ctx.locals.caller);
  return taskReference(job.id);
}

async function getTask(taskId, ctx) {
  return reportJobs.getForCaller(taskId, ctx.locals.caller);
}
```

**Recommendation.** Implement the MCP protocol once and let apps supply execution and storage. The setup cost is a provider, so make both recipes short and exercise them before expanding the contract. Don't carry `promoteAfter`, the prototype store, or a scheduler into the framework.

### 7.9. App-owned task administration and reporting

Status: ✅

Operators need to find work and act on it. That is a real use case, but the provider owns the records and their meaning.

**Context.** Job inputs, results, errors, and tags are app-defined. The framework can't assume which fields may be shown or how retry should behave after an attempt partially succeeded. Providers may not use SQL at all.

**Options and previews.** A built-in dashboard or admin API could list yesterday's failed webhooks and retry 50 of them, but would require standard storage fields and action rules. An opt-in read-only SQL endpoint would support richer reporting, but ties the consumer to a connection and schema and doesn't handle task actions. An app can instead expose a guarded failed-job report and pass selected IDs to its own bulk retry operation. If it wants pass-through SQL, it chooses the reporting connection and who can query it.

**Recommendation.** Let apps own reporting and management. Keep mutations in app task operations so they recheck permissions and state and can audit the change. Don't define a built-in admin API, dashboard, SQL endpoint, or generic database adapter. The ordinary route and guard extension points already let consumers build them.

### 7.10. Package and repository placement

Status: ✅

Keep one repository, one `argsbarg` package, one public entry point, and one release line. Optimize for a simple install and API, not unmeasured bundle size.

**Context.** CLI, HTTP, and MCP share schema validation, invocation, guards, outcomes, and cancellation. HTTP and MCP also share an HTTP server. Shipping those together avoids version negotiation between packages that regularly change together. Keep code together where it makes the flow easier to follow or enforces the same rule; don't extract a shared helper just because two transports currently look alike.

**Chosen layout preview.** All public imports come from `argsbarg`. Keep the transport-specific source where it reads best, without public subpaths or package boundaries. A CLI-only invocation may load server modules in plain Node; importing them must not start a listener, register global hooks, or do server setup.

```text
argsbarg/
├── package.json         # one public export: "."
└── src/
    ├── index.ts         # public API for all surfaces
    ├── runtime/         # shared invocation and CLI runtime
    ├── server/          # Shared HTTP dispatch, binds, and shutdown
    ├── http/            # HTTP-specific routing and responses
    └── mcp/             # MCP-specific protocol and transports
```

**Alternatives.** Public subpaths such as `argsbarg/http` would let a CLI-only Node app avoid loading server modules, but add imports and API entry points to maintain. Bundlers may remove unused, side-effect-free code; npm still installs the whole package, and plain Node doesn't tree-shake static imports. Separate packages would isolate dependencies and install size at the cost of package wiring and compatibility checks. This is what that rejected split would look like:

```text
argsbarg/
├── package.json         # workspace and coordinated release
└── packages/
    ├── core/            # CLI and invocation contract
    ├── listener/        # shared by HTTP and MCP-over-HTTP
    ├── http/            # depends on core and listener
    └── mcp/             # depends on core; uses listener for HTTP, not REST
```

**Recommendation.** Take the simpler root import. Revisit subpaths only for a measured startup or bundle problem. Revisit separate packages only if there is a concrete dependency, runtime-version, or installation constraint that subpaths won't solve.

### 7.11. Startup commands and distribution

Status: ✅

Startup should be obvious from the command. Installing a plugin shouldn't turn a normal CLI invocation into a server.

**Context.** Existing 8.x apps have `http` and `mcp` launch commands. Agent-plugin manifests and `.mcpb` bundles supply a command and args for stdio, while gateway bundles need a defined loading contract. The new in-process `api` and `mcp call` commands don't start transports.

**Decision.** Ship one executable per app for CLI commands, the shared HTTP server (serving whichever of `http`, `jsonRpc`, and `mcp` over HTTP are enabled), and MCP stdio. Whenever any service plugin (`http`, `jsonRpc`, or `mcp`) is configured, `serve` as the first positional argument (`{app} serve ...`) is the standardized convention that enters long-lived service mode and stays running until shutdown (`SIGINT`/`SIGTERM`), then drains active calls and resolves `app.run()`. Running a CLI command or a local CLI mirror never starts a server. Plugin manifests and `.mcpb` bundles pass stdio launch arguments (`serve mcp --stdio`) to the same executable instead of shipping a dedicated MCP program. An app can enable both MCP launch modes, but each process starts only its selected transport. To run both at once, use separate processes. Don't accept a combined launch or silently choose one transport if both are requested.

```sh
myapp report --project alpha
myapp serve http          # Shared server for enabled HTTP surfaces (/api, /rpc, /mcp)
myapp serve mcp --stdio   # JSON-RPC over stdin/stdout; no HTTP listener
```

**Discarded: separate executables.** `myapp-http` and `myapp-mcp` would make each process's role obvious and avoid reserving `serve` in the CLI tree. That doesn't justify additional entry points to build, install, and configure. One executable gives users a single command to install and keeps process separation available through launch arguments.

**Still to specify.** Exact sub-flags under `serve` (e.g., selecting HTTP vs stdio).

**Discarded: runtime `argsbarg gateway` bundle loader.** Drop `argsbarg gateway` and the 8.x `mcpGatewayRegistry` `globalThis` hook completely (see [gateway bundles vs child mounts](./2026.11.19%20-%20Gateway%20bundles%20vs%20child%20mounts.md)). Multi-app composition in one executable uses build-time `children` mounts instead.

### 7.12. Breaking major without an 8.x migration path

Status: ✅

Design a breaking major release. Backward compatibility and providing a migration path are both out of scope.

**Context.** 8.x derives routes and tools from the CLI tree and has different guards, launch commands, and wire behavior. Existing code and prototypes are useful references for behavior that fits the new design. They don't define the public contract or acceptance tests for the new release.

**Discarded approaches.** An adapter that translates 8.x declarations would preserve the coupling this design removes. Old command aliases, dual bundle formats, or legacy wire behavior would make the new release maintain two contracts. Even a documented before/after migration would add a second deliverable that this plan doesn't need.

**Decision.** No shims, legacy aliases, old-bundle support, migration tooling, or migration guide. Provide new-release examples and test the new contract. Existing users can pin a published 8.x version; that is not a commitment to maintain an 8.x line. Testing current clients against the new MCP revision remains in scope.

### 7.13. MCP protocol revision for the new plugin

Status: ✅

The new plugin needs a clear MCP version contract. Supporting an older host and preserving an older app aren't the same decision.

**Context.** Released 8.x supports legacy initialization and session behavior. The `toolbarg` experiment targeted `2026-07-28`, using `server/discover`, per-request version and client capabilities, and the newer result shape. Wire-harness success doesn't establish that an editor or agent host speaks that revision.

**Options and previews.** A multi-revision plugin would accept an older client's `initialize` and a newer client's `server/discover`, keeping more hosts in range but carrying two lifecycle and result paths. The modern-only plugin uses the new wire contract and rejects unsupported versions clearly.

**Decision.** Target `2026-07-28` only. Implement its stateless wire contract: `server/discover`, per-request protocol version and capabilities in `_meta`, `resultType` replies, required `CacheableResult` metadata (`ttlMs`, `cacheScope`) with deterministic `tools/list` ordering (aligned with the fixed catalog in [7.22](#722-explicit-gateway-contracts-and-composition-scope)), and standard Streamable HTTP `Mcp-Method` / `Mcp-Name` request headers. Dropping the legacy `initialize` handshake also drops startup `roots/list` cwd discovery; local stdio tools rely on process launch `cwd` or explicit path inputs instead. Verify discovery, tool calls, cancellation, and task capability negotiation in actual hosts before release. Report gaps in client support without adding a legacy protocol path.

### 7.16. Input binding and shared invocation

Status: ✅

**Decision.** Choose A: each surface binds inputs and encodes results at its own boundary. A shared runner validates inputs, applies guards, and calls the handler. Route guards and handlers receive one typed `ctx.inputs` object, just like commands and tools. Exact input, guard, and outcome signatures remain open with [7.1](#open-api-choices).

[Approach C](#approach-c-use-a-surface-neutral-factory) gives each command, route, and tool its own declaration. Neither option below derives HTTP or MCP inputs from argv or adds a required operation layer. The snippets show internal boundaries, not public API commitments.

A local CLI mirror keeps the declaration's contract without pretending to arrive through its native transport. For example, `myreports api POST /api/projects/alpha/reports` binds the route inputs, and `myreports rpc reports.generate` binds the JSON-RPC method params, while their guards use local env instead of fabricating HTTP headers. Neither mirror creates fake headers or argv to reuse another adapter.

#### Option A: Native binding, shared guarded invocation

Each adapter identifies a declaration, binds values from their declared sources, and passes those values and the actual invocation context to the same runner. Guards and handlers receive one typed `ctx.inputs` object, including for REST:

| Entry | What the adapter reads | Validated `ctx.inputs` for the guard and handler |
| --- | --- | --- |
| `myreports report alpha` | argv positional `projectId`: `alpha` | `{ projectId: "alpha" }` |
| `POST /api/projects/alpha/reports?dryRun=true` with body `{"format":"pdf"}` | Path `id`: `alpha`; query `dryRun`: `true` (text); JSON body `format`: `"pdf"` | `{ id: "alpha", dryRun: true, format: "pdf" }` |
| `tools/call` for `generate_report` | MCP arguments: `{"projectId":"alpha"}` | `{ projectId: "alpha" }` |

The route declares path, query, and body separately and OpenAPI describes them separately. Bind and validate each field from its declared source, then combine the typed fields into one flat object. Reject route declarations that map multiple sources to the same key; a body `id` can never override the path `id`. The route and its mirrors deliver the same `ctx.inputs` shape without changing their wire contracts.

The adapter handles malformed wire requests before they reach the runner:

```typescript
// CLI
const commandArgs = bindCli(reportCommand, argv);
return writeCli(await invokeBound(reportCommand, commandArgs, cliContext));

// REST
const routeArgs = await bindHttp(reportRoute, request);
return writeHttp(await invokeBound(reportRoute, routeArgs, httpContext));

// MCP, after envelope and capability checks
const toolArgs = bindMcp(generateReportTool, call.arguments);
return writeMcp(await invokeBound(generateReportTool, toolArgs, mcpContext));
```

The runner validates against the selected declaration, enforces the applicable guards, and calls the handler with validated inputs and typed per-call values. It returns an outcome rather than writing to stdout or encoding HTTP or MCP errors. For example, a guard denial stays a denial until the adapter encodes it: CLI can print a diagnostic and return a nonzero exit; REST can preserve a challenge status and headers; an RPC mirror can deny one batch member without changing its neighbors' results.

The runner doesn't force all successful results into one shape. A typed tool result, an HTTP download, and a CLI result can keep their surface-specific contracts. An HTTP stream must reach the HTTP encoder without being buffered into JSON. The shared boundary needs to carry the declaration's input and result types without allowing one surface's outcomes on another.

**Handler errors and non-200 HTTP responses.** Handlers throw one lightweight framework error (for example, `AppError` / `notFound(...)` with code, message, and optional HTTP status) for domain/application failures (`404`, `409`, `403`, etc.); each surface encodes it natively (REST -> HTTP status + JSON error body, JSON-RPC -> RPC error object, MCP -> tool error `isError: true`, CLI -> stderr + non-zero exit). For non-200 HTTP successes (`204 No Content`, `201 Created`, custom headers, downloads, streams), REST route handlers return a standard Web `Response` directly (for example, `new Response(null, { status: 204 })`).

#### Option B: Each surface owns execution as well as binding

Each adapter uses common validators and app code but decides when to validate, apply guards, call the handler, and encode the result. For the report route and tool, that looks like:

```typescript
const routeInputs = await parseHttp(reportRoute, request);
const routeLocals = await authorize(reportRoute, routeInputs, httpContext);
return writeHttp(await reportRoute.handler({ ...routeInputs, ...httpContext, locals: routeLocals }));

const toolInputs = parseMcp(generateReportTool, call.arguments);
const toolLocals = await authorize(generateReportTool, toolInputs, mcpContext);
return writeMcp(await generateReportTool.handler({ inputs: toolInputs, ...mcpContext, locals: toolLocals }));
```

These are separate adapter sketches; each must also handle validation failures and denials before calling the handler. This puts each call path in one place and avoids a shared outcome type. The cost is repeated orchestration: if one adapter forgets a mount guard, validates at a different point, or bypasses a guard in a mirror, operations with the same declarations drift. A shared dispatcher base class could centralize that sequence, but would also pull otherwise unrelated adapter lifecycles into one abstraction.

**Verification.** Check that REST and its mirrors give guards and handlers the same flat inputs, reject overlapping declarations, and never let a body or query value supply a path field. Native and mirrored calls must reject invalid inputs and denials before handler side effects, use the actual credential source for each entry, and preserve native outcomes, including a streaming HTTP response and an MCP tool result.

### 7.19. MCP transport adapters

Status: ✅

**Settled boundary.** Use separate internal stdio and Streamable HTTP adapters over one MCP dispatcher. `myreports` declares `generate_report` once. The dispatcher owns protocol validation, capabilities, and tool and task dispatch; each adapter owns its I/O and supplies caller context and cancellation per call. Don't expose a generic transport interface. Keeping launch selection out of the tools and dispatcher leaves room for a future dual launch without reserving any public API for it.

**Decision.** Use Option A. Attach middleware directly to the MCP HTTP mount. It can return an HTTP denial before dispatch or pass a verified caller to MCP tool guards and task providers. It doesn't apply to stdio, `/api`, or `/rpc`. The [factory](#approach-c-use-a-surface-neutral-factory) still owns normal startup. The following signatures are illustrative.

#### Option A: Middleware on the MCP HTTP mount

The app attaches its verifier at the point where it enables MCP over HTTP:

```typescript
const app = argsbarg({
  ...metadata,
  http: { routes: [reportRoute] },
  mcp: {
    stdio: true,
    http: { middleware: protectMcp },
    tools: [generateReportTool],
  },
});
await app.run();
```

Here `stdio: true` and `http: { ... }` make both modes available. Startup takes only one branch:

```typescript
const dispatchMcp = createMcpDispatcher(registry);

if (launchMode === "mcp-stdio") {
  await serveStdio(io, dispatchMcp);
} else if (launchMode === "http" && mcpHttpEnabled) {
  router.mount("/mcp", createMcpHttpHandler({ dispatchMcp, middleware }));
}
```

Stdio keeps its frame reader, write queue, and output isolation. HTTP inspects methods and headers — including `2026-07-28`'s `Mcp-Method` and `Mcp-Name` headers before parsing the JSON-RPC body — authenticates before protected dispatch, and owns response codes, streaming, and request aborts. The middleware can return an HTTP denial without dispatching a message, or supply a verified caller for that request only. Disconnecting an HTTP client ends its request or stream; it doesn't close the dispatcher or cancel a durable task. No listener opens in stdio mode.

Mount-local config makes it clear that `protectMcp` doesn't apply to `/api`, `/rpc`, `stdio`, or `myapp mcp call`. `stdio` and the local mirror still run the MCP surface and tool guards under the same composition rules; a protected tool must deny the call if that path hasn't established a verified caller. Share policy in the guards and credential verification in ordinary app code rather than simulating an HTTP request. See [7.1](#open-api-choices) and the [guard composition note](./2026.11.19%20-%20Guard%20composition%20and%20caller%20handoff.md). The app needs a separate way to publish supporting routes such as OAuth resource metadata; compare that with [7.21](#721-oauth-for-mcp-over-http).

#### Option B: Scope shared HTTP middleware to `/mcp`

The app uses the server's general middleware API to express the same policy:

```typescript
const app = argsbarg({
  ...metadata,
  server: {
    middleware: [{ path: "/mcp", use: protectMcp }],
  },
  http: { routes: [reportRoute] },
  mcp: { stdio: true, http: true, tools: [generateReportTool] },
});
await app.run();
```

This keeps routing, middleware, and metadata on one HTTP API, but makes apps scope MCP policy by matching a path and reasoning about middleware order. Option A keeps that boundary explicit without deciding how general HTTP middleware works.

**Still open.** Finalize the middleware signature and typed caller handoff with [7.1](#open-api-choices). The [opt-in OAuth helper](#721-oauth-for-mcp-over-http) uses this mount boundary.

**Verification.** Run the same tool on each transport in separate processes. Check that middleware denies unauthenticated HTTP requests before dispatch, passes the verified caller to MCP tool guards and task providers, and doesn't run for stdio or sibling routes. Request aborts must not end neighboring calls or durable work.

### 7.20. App-supplied task provider

Status: ✅

**Decision.** Use Option A. The tool starts work through app code and explicitly returns a task reference. The app supplies named `get`, `update`, and `cancel` callbacks for the standard methods in the [MCP Tasks extension](../../../../docs/mcp.md#tasks). Argsbarg handles the [wire protocol](#mcp-task-providers); the app owns execution, storage, and authorization.

The provider isn't the app's entire job API. For example, an app can add a guarded `retry_report` tool that uses the same job service and returns a new task reference. `tasks/update` only answers pending input requests. Additional standard methods can get named callbacks if argsbarg adopts them; this provider doesn't register arbitrary wire methods.

#### Option A: Named provider operations and an explicit task return

`reportJobs` is the app's own job service, not an argsbarg API. It can wrap [in-memory state or a durable queue](../../../../docs/use-cases/tasks.md). Register the follow-up operations once, then use the negotiated task context to return a reference:

```typescript
const exportReport = {
  name: "export_report",
  description: "Export a project report.",
  inputSchema: Project,
  outputSchema: ReportExport,
  guard: requireReporter,
  async handler({ inputs, locals, signal, mcp }) {
    if (!mcp.tasks.available) {
      return exportInline(inputs.projectId, locals.caller, signal);
    }

    const job = await reportJobs.enqueue({
      projectId: inputs.projectId,
      actorId: locals.caller.id,
      workspaceId: locals.caller.workspaceId,
    });
    return mcp.tasks.reference(job.snapshot);
  },
};

const app = argsbarg({
  ...metadata,
  mcp: {
    stdio: true,
    http: { middleware: protectMcp },
    tools: [exportReport],
    tasks: {
      get: ({ taskId, caller, signal }) =>
        reportJobs.getForCaller({ taskId, caller, signal }),
      update: ({ taskId, caller, inputResponses, signal }) =>
        reportJobs.submitInputForCaller({ taskId, caller, inputResponses, signal }),
      cancel: ({ taskId, caller, signal }) =>
        reportJobs.requestCancelForCaller({ taskId, caller, signal }),
    },
  },
});
```

`reportJobs.enqueue` must make the task visible to `get` before returning its ID. The reference helper encodes that existing task; it doesn't start or persist it. The inline result and the completed task result both describe the export. A task-only tool would return a capability error rather than use the inline branch; it must do so before creating work. `mcp.tasks.available` stands for both the registered provider and this client's opt-in, not merely the fact that the server supports tasks.

For `tasks/get` on a later connection, argsbarg validates the request and hands the provider a freshly verified caller, not raw credentials or the identity captured on the first request. The provider verifies ownership for `get`, `update`, and `cancel`. Those handlers' `signal`s apply to the individual follow-up calls. The worker uses separate cancellation, and a cancellation acknowledgement isn't a promise that the job has already stopped.

#### Option B: One typed callback for all task operations

The tool still starts the same job and returns a reference, but one discriminated callback replaces the provider object:

```typescript
async function handleTask({ caller, signal, operation }: TaskRequest<Reporter>) {
  switch (operation.kind) {
    case "get":
      return reportJobs.getForCaller({ taskId: operation.taskId, caller, signal });
    case "update":
      return reportJobs.submitInputForCaller({
        taskId: operation.taskId,
        inputResponses: operation.inputResponses,
        caller,
        signal,
      });
    case "cancel":
      return reportJobs.requestCancelForCaller({ taskId: operation.taskId, caller, signal });
  }
}

const mcp = { stdio: true, tools: [exportReport], tasks: handleTask };
```

One callback matches an app that already routes task commands as events. For simpler providers it makes every app write the switch and makes operation-specific return types less obvious. A provider base class would add a framework lifecycle without helping either storage recipe; an app can use its own class behind either shape.

**Still open.** Finalize the provider signatures, verified caller handoff, and typed task-return helper against both recipes. The code above illustrates the shape, not finalized signatures.

**Verification.** Check that a client without the capability doesn't start task-only work, a second caller can't inspect or modify the first caller's task, and a durable task remains pollable after reconnect or restart without the original request's credentials.

### 7.21. OAuth for MCP over HTTP

Status: ✅

**Decision.** Use Option B: provide a small, opt-in OAuth resource-server helper for hosted `/mcp`, built on the [mount-local middleware hook](#719-mcp-transport-adapters). Apps with an existing resource-server integration can use the hook directly. Argsbarg serves Protected Resource Metadata, sends standard HTTP challenges, and passes the verified caller to tool guards and task providers. The app supplies token verification and authorization policy. Argsbarg does not manage users, issue tokens, or store them.

The external issuer handles login and token issuance; the harness handles refresh if the issuer provides a refresh token. This decision covers harness authentication to the app's public `/mcp` only. It doesn't apply to stdio, grant access to `/api` or `/rpc`, or forward the inbound token to upstreams. A tool asking the user to connect an upstream account is covered separately in [7.24](#724-browser-sign-in-for-upstream-accounts).

#### Option A: App-owned integration via middleware

The app's authentication library verifies the token against the configured issuer and resource. The app supplies middleware for `/mcp` and publishes Protected Resource Metadata on the shared HTTP server. The helper names in this sketch refer to app code:

```typescript
const resource = "https://reports.example/mcp";
const issuer = "https://login.example";
const metadataUrl = "https://reports.example/.well-known/oauth-protected-resource/mcp";

const protectMcp: McpHttpMiddleware<Reporter> = async (request, next) => {
  const auth = await verifyMcpBearer(request.headers, { issuer, resource });
  if (!auth.ok) return mcpChallenge(auth.failure, metadataUrl);
  return next({ caller: auth.caller });
};

const app = argsbarg({
  ...metadata,
  server: {
    additionalRoutes: [protectedResourceMetadataRoute(metadataUrl, { resource, issuer })],
  },
  mcp: { http: { middleware: protectMcp }, tools: [generateReportTool] },
});
```

This works with an existing auth stack and gives the app control of public URLs and policy behind a proxy. The important test of the middleware seam is whether it can do this without replacing the MCP dispatcher or binding another listener. The cost is that every hosted app needs correct metadata and challenges, not just token verification.

#### Option B (selected): Argsbarg owns the MCP-specific resource-server wiring

An optional helper configures the same HTTP boundary. The app still supplies a verifier for its issuer and app-specific policy:

```typescript
const app = argsbarg({
  ...metadata,
  mcp: {
    http: {
      oauth: {
        resource: "https://reports.example/mcp",
        authorizationServers: ["https://login.example"],
        verifyAccessToken: verifyReportAccessToken,
      },
    },
    tools: [
      { ...listReports, guard: requireScope("reports:read") },
      { ...exportReport, guard: allOf(requireScope("reports:export"), canExportProject) },
    ],
  },
});
```

The helper serves resource metadata and maps absent or invalid credentials to an HTTP `401` with a bearer challenge pointing to that metadata. The app's verifier checks token validity, issuer, expiry, and intended audience, and returns a typed caller or an explicit failure. The app's guards can request a `403` with `insufficient_scope` for a missing OAuth scope where step-up is supported. To make that possible, the `/mcp` HTTP adapter must finish running mount and tool guards *before* starting a `200 text/event-stream` response; once SSE streaming begins, an HTTP `403` challenge can no longer be sent. A project-access denial for an otherwise valid caller should not trigger reauthentication. This saves app wiring but makes argsbarg responsible for metadata routing, challenge semantics, and host interoperability. For example, both options should produce the same initial challenge for this app:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://reports.example/.well-known/oauth-protected-resource/mcp"
```

Because `mcp.http.oauth` runs only on `/mcp`, a tool that is also reachable via `stdio` or `myapp mcp call` won't receive an OAuth-verified caller on those local entry points. Those entry points need their own credential handling (via `mcp.guard` or the tool guard); exact guard composition and typed caller handoff remain open in [7.1](#open-api-choices) (see [guard composition and caller handoff](./2026.11.19%20-%20Guard%20composition%20and%20caller%20handoff.md)).

The harness uses the metadata to find the issuer, signs in, and retries with `Authorization: Bearer <access-token>`. If the issuer supplies a refresh token and the harness supports renewal, the harness refreshes with the issuer and the resource server only sees the renewed access token. A JSON-RPC tool error cannot substitute for the HTTP challenge.

**Still open.** Finalize the helper, verifier, and guard signatures with [7.1 startup and caller context](#open-api-choices). The sketch is illustrative.

**Verification before shipping.** Use an actual harness and issuer to check discovery, browser sign-in, a successful tool call, harness-managed refresh after expiry, and wrong-audience rejection before dispatch. Check that a missing scope gets the appropriate challenge and that a valid caller denied access to a project isn't prompted to sign in again. See the [hosted OAuth verification requirements](#oauth-for-hosted-mcp).

### 7.22. Explicit gateway contracts and composition scope

Status: ✅

**Zod expectations.** Declare public gateway input schemas and any published structured output schemas in Zod. The app supplies explicit command, route, or tool bindings and handlers. Argsbarg validates inputs and generates discovery from those same declarations. Apps may write Zod by hand or generate and review it at build time outside argsbarg. Raw JSON Schema, OpenAPI documents, and upstream MCP tool lists are not registration inputs.

**Intentionally unsupported in the next major:**

- Native external schema import or reflection, including at startup; live catalog updates; and per-caller catalogs.
- Transparent protocol federation or generic forwarding of upstream streams, subscriptions, sessions, and tasks.
- Merging running child apps or automatically combining their OAuth config, task stores, or lifecycle hooks.

The catalog stays fixed while the app runs. Apps can use owner settings to omit declarations at startup; omitted entries are neither discoverable nor callable. Guards still apply saved user preferences and policy per call without changing discovery. See [app settings and user preferences](../../../../docs/use-cases/settings.md). Apps can call and combine upstreams using their own clients, and implement streaming or task handling where their public surfaces support it. Mounted children still contribute declarations, guards, and scoped inputs, and discovery is generated from those declarations. The mount API remains part of [7.1](#71-app-model-composition-and-lifecycle).

**Tradeoff.** Updating a public contract requires changing the app's declarations and restarting. In exchange, upstream metadata changes cannot silently change what clients see or what validation accepts.

### 7.23. Intent-first app authoring skills

Status: ✅

**Decision.** Maintain a bootstrap skill in the argsbarg repo for new apps and ship one shared upsert skill with the templates for existing apps. The upsert skill also works in apps that weren't scaffolded. Keep `argsbarg create` as deterministic scaffolding; the skills guide personalization, adding or removing surfaces and operations, pivots, and upgrades. A request for advice alone doesn't authorize edits.

1. Establish the desired outcome and what must stay unchanged before deep discovery. If intent is clear, proceed. If it isn't, read only enough local context to ask a focused question. For example, "remove MCP" may mean stop shipping a plugin, disable one transport, or remove MCP entirely.
2. Once scope is clear, inspect the relevant code, tests, and docs for the app's installed argsbarg version. Use the [use-case guides](../../../../docs/use-cases/README.md) to compare options. Make requested changes in place, keep unrelated behavior intact, and avoid duplicating work when the request is repeated.
3. When an update could matter, check published npm versions and the official GitHub changelog. Ignore `[Unreleased]`; surface fixes that are urgent for the app or relevant to the request. If the check is unavailable, continue on the installed version where possible. Don't change dependencies or lockfiles without authorization.

**Verification.** Bootstrap a small CLI, then add an MCP tool to an existing app without changing its other surfaces or packaging. Repeat the request without creating duplicates. For an ambiguous removal, check that the skill clarifies scope before broad research or edits.

### 7.24. Browser sign-in for upstream accounts

Status: ✅

**Decision.** Support both paths. Recommend A when the harness supports [URL-mode elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation#url-mode-elicitation-requests) and can retry through MCP's [multi-round-trip flow](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) or let the user retry after sign-in. Use B as the app-owned fallback when the harness can't handle A, not as an automatic fallback when the user declines. See the [Billing connection scenario](../../../../docs/use-cases/gateway.md#connect-an-upstream-account-mid-call).

| Option | What the app author supplies | What the harness does |
| --- | --- | --- |
| A. Typed URL prompt and continuation | The tool returns an app-generated sign-in URL and opaque continuation state. Argsbarg checks the client capability, encodes `input_required` with URL-mode `elicitation/create`, and delivers the response and echoed state on a new invocation. | Shows the destination, asks for consent before opening it, and can retry the tool. The original call doesn't stay open. |
| B. Separate connect and rerun | The tool returns an ordinary tool error with a sign-in link and instructions for rerunning it. No new argsbarg API or continuation state is needed. | Displays the instructions; the user completes sign-in separately and runs the tool again with the same arguments. |

**Tool schemas stay unchanged.** Both paths publish the same `inputSchema` and success `outputSchema`. A carries the URL prompt, response, and continuation state in MCP protocol fields outside the tool arguments and successful result. B carries the link and instructions in the tool error. Don't add auth fields to the tool schemas or a success variant for “sign-in required.”

With either option, the app owns the upstream OAuth flow, callback, and credential handling. On retry, it reauthorizes the caller, validates any continuation state against the caller and originating operation, and checks for a usable grant for the intended upstream. An `accept` response isn't proof of a grant. A missing grant doesn't cause an inbound `/mcp` challenge under [7.21](#721-oauth-for-mcp-over-http). This isn't a generic upstream OAuth helper or an MCP Tasks requirement.

The exact API for A and whether it ships in the first release remain open until verified with a real harness and OAuth upstream.

**Verification.** Record the harness and version. Exercise consent followed by a retry before the callback, then a successful retry after the callback. Verify decline or cancel, the manual fallback on a harness without URL-mode support, and expired, tampered, or cross-caller continuation state. Compare `tools/list` with and without URL-mode support and with and without a Billing grant: both published schemas must be identical. Billing must not be called with a missing grant, and repeated tool requests must not duplicate side effects.

### 7.25. App config directory helper

Status: ✅

**Decision.** Offer an opt-in argsbarg config-directory helper (e.g., `resolveConfigDir`), with the exact signature still open. Resolve one absolute app directory: an explicit app-provided override wins (for example, from `MYREPORTS_CONFIG_DIR`); otherwise use `$XDG_CONFIG_HOME/<app>` on Linux (default `~/.config/<app>`), `~/Library/Application Support/<app>` on macOS, or the user's Roaming AppData directory (`%APPDATA%\<app>`) on Windows. Don't probe for an existing directory, infer a Homebrew prefix, or switch paths based on the install or workspace. Reject an invalid explicit override rather than falling back.

Keep it KISS: `resolveConfigDir` creates the resolved directory directly (`mkdir(..., { recursive: true })`) when called — no extra startup-lifecycle wiring, no skipping for `--help`/version/completions, and no extra `stat` pre-check. Because the helper is opt-in, apps control when they call it. Mounting a child doesn't implicitly call the child's helper.

The app still owns file names, schema, loading, saving, and user data. A local app may keep owner settings and user preferences in the same directory; a hosted app should keep owner settings separate from user-writable data. [7.22](#722-explicit-gateway-contracts-and-composition-scope) allows config-only visibility changes for features the author has wired into startup, not arbitrary name-based masking in apps that haven't opted in.

**Verification and docs.** Check platform defaults, explicit override precedence, directory creation and reuse, and invalid-override rejection without fallback. Check that editing owner settings and restarting updates discovery and dispatch together. Update the [configuration guide](../../../../docs/cli-program.md#app-settings) and [settings use cases](../../../../docs/use-cases/settings.md) with the final API and examples when implemented.

## Behavior and verification reference

This reference preserves the detailed behavior and examples that the designs need to account for. It doesn't commit to a particular app root, declaration shape, or sequence of work. The separate implementation plan can use these examples to derive acceptance checks once the open decisions are settled.

### Packaging and startup

A newly installed app can run CLI-only, REST-only, JSON-RPC-only, MCP stdio, or MCP HTTP, and can share one HTTP server between REST, JSON-RPC, and MCP. Route and command name conflicts are startup errors, not a matter of registration order. Agent-plugin and `.mcpb` launches select explicit stdio mode (`serve mcp --stdio`) on the same app executable. Runtime `argsbarg gateway` bundle loading is removed; multi-app executables use build-time `children` mounts. CLI behavior examples cover options, positional inputs, help, completion, `--json`, and local invocation.

Preparing declarations and showing help don't open app resources. Resolve HTTP listener settings only in HTTP mode, never from request headers. Report invalid bind config instead of falling back to another address. Report ready only after all requested binds succeed; on failure release partial binds. If Unix sockets are selected, put them in a restricted directory, report a pre-existing path instead of unlinking it, and remove only the socket owned by this runtime. Socket permissions don't replace app guards.

Stop or drain active calls before releasing app resources, and don't close dependencies borrowed from the app. `app.run()` sets `process.exitCode` (or returns the exit code) and resolves normally rather than calling `process.exit()`, so app-owned `try/finally` cleanup runs after CLI invocations, local mirrors, and graceful server shutdown. Separate CLI and HTTP processes don't share memory; two runtimes in one process share app dependencies only when the caller provides the same instance. Transport shutdown doesn't end app-owned durable jobs.

The [experiment record](./2026.11.17%20-%20Concurrent%20calls%20and%20background%20tasks.md) preserves what the disposable local copies showed: `../clibarg` was an unpruned CLI baseline, `../httpbarg` explored async HTTP jobs, and `../toolbarg` exercised MCP `2026-07-28` and Tasks on the wire. The design and its verification must work after those checkouts are gone. Their separate package layout, task engines, and SQLite stores are outside the next-major design.

In this repo, [`httpRequestToArgv`](../../../../src/http/routes.ts) and [`mcpToolCallToArgv`](../../../../src/mcp/tools.ts) show the round trip direct schema binding should eliminate. [`invocation-scope.ts`](../../../../src/runtime/invocation-scope.ts) holds the concurrency fix.

### Invocation context and guards

| Call arrives through | Source available to the call context |
| --- | --- |
| CLI, including an in-process mirror | `ctx.env.get(name)` reads process environment |
| MCP stdio | `ctx.env.get(name)` reads process environment |
| HTTP, including `/api`, `/rpc`, and `/mcp` | `ctx.headers.get(name)` reads headers on that request |

Root calls can read any key from the applicable source; [mounted child calls](../../../../docs/use-cases/child-apps.md) use a prefixed view of that same source. Preserve source lookup rules, including case-insensitive HTTP header names. On HTTP and remote `/mcp`, static header forwarding (such as `Billing-Authorization` or custom API-key headers configured via harness `headers` settings or custom HTTP clients — see [MCP harness notes](../../../../docs/mcp/harness/README.md)) works cleanly with child-mount prefix stripping; OAuth-managed `/mcp` still relies on standard `Authorization` at the suite boundary. Never merge sources or fall back from a missing header to server env. Keep raw values out of framework logs and serialization. App code can still read process env directly when it needs startup configuration; that access isn't scoped by the mount.

Apps choose what credential to require, how to verify it, and which typed values, such as caller and workspace, to give the handler. Argsbarg reserves no token name or identity model. An app can require a credential for an in-process call; this doesn't change OS permissions on the app's database.

Guards run before a handler or provider can have side effects. At the HTTP boundary a guard can deliberately return status, headers, and body; CLI, JSON-RPC, and MCP report denials in their native forms. A denied operation in a JSON-RPC batch doesn't rewrite the response for neighboring calls. The current wire `onRequest` hooks are observe-only, so they don't cover this contract. Apply surface and operation guards to the enabled mounts and the matched operation, including when it is reached through a local CLI mirror. Keep verified caller values, progress, cancellation, and captured output per invocation. A long call must not block a second call that can unblock it. Preserve the restriction on `process.chdir` during overlapping calls and keep handler logs off the MCP wire.

### HTTP routes, JSON-RPC methods, and CLI mirrors

| Surface | Network call | Local CLI mirror | Discovery |
| --- | --- | --- | --- |
| REST (`http`) | `POST /api/reports` with a JSON body | `myapp api POST /api/reports` with JSON on stdin | `/api/openapi.json`, `/api/docs` |
| JSON-RPC (`jsonRpc`) | `POST /rpc`, method `reports.generate` | `myapp rpc reports.generate` with JSON on stdin | `/rpc/openrpc.json` |

Custom REST routes live under `/api`, with `/api/openapi.json` and `/api/docs`. `/health/liveness`, `/health/readiness`, and `/status` live at the root of the shared server; standalone JSON-RPC (`/rpc`) and MCP (`/mcp`) are sibling mounts. REST path, query, and JSON body have separate Zod declarations and bind to one typed input object, with no overlapping keys (see [7.16](#716-input-binding-and-shared-invocation)). Document query coercion. Preserve HTTP statuses, headers, and binary bodies.

The REST CLI mirror takes a method and exact full path, including query string: `myapp api GET /health/readiness` or `myapp api POST /api/reports`. It reads JSON from stdin, adds no hidden prefix, and opens no listener. It uses the same validation and guards with CLI env context, not fabricated request headers. HTTP downloads, NDJSON, and SSE support backpressure and disconnect handling; the CLI mirror pipes the response body without buffering it all. A disconnect ends the transport stream, not an app-owned durable job. WebSockets and streaming uploads are deferred.

#### Standalone JSON-RPC surface and discovery

The `jsonRpc` surface mounts `POST /rpc` on the shared HTTP server and publishes `/rpc/openrpc.json` describing its declared methods. Methods are declared explicitly with their own names, Zod `inputSchema`, optional `outputSchema`, and guards — REST routes are not automatically mirrored to JSON-RPC.

The wire boundary handles IDs, notifications, errors, and batches. Each batched call is independently validated and authorized; batching doesn't imply order or atomicity. The local CLI mirror `myapp rpc <method>` reads JSON params from stdin and invokes the method in-process with local env context and no listener.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "reports.get",
  "params": { "id": "r42" }
}
```

### MCP tools and their CLI mirror

The same tool declarations can serve stdio or Streamable HTTP in separate processes. `/mcp` is on the shared HTTP server and doesn't require REST or JSON-RPC. Stdio starts no listener and writes only protocol output to stdout. HTTP reuses server guards and streaming; MCP owns framing and its JSON-RPC messages. The [selected revision](#713-mcp-protocol-revision-for-the-new-plugin) uses `server/discover`, per-request version and capabilities in `_meta`, `resultType` replies, required `CacheableResult` fields (`ttlMs`, `cacheScope`) with deterministic `tools/list` ordering, standard `Mcp-Method` and `Mcp-Name` HTTP headers, and actionable unsupported-version errors. It has no legacy initialization, roots-based cwd discovery (local stdio tools rely on process launch `cwd` or explicit path arguments), or output wrapper. Tool arguments bind directly to Zod; the wire adapter handles MCP's object-rooted input requirement and wrapping when the input schema needs it.

| Interface | Invocation and discovery |
| --- | --- |
| MCP stdio or `/mcp` | `tools/call`, `server/discover`, and `tools/list` |
| Local CLI mirror | `myapp mcp call <name>` with JSON on stdin; no server needed |

Both call the same registered tool through its validation and guards. CLI uses local env context. MCP tools do not auto-generate plain HTTP `/tools/{name}` endpoints or `/tools/openapi.json`, and there is no `/mcp/openrpc.json` (a tool is an argument to `tools/call`, not a standalone RPC method). Expose operations only on configured surfaces and derive discovery and schemas from the operations actually registered there.

### OAuth for hosted MCP

This is the behavior to verify for the [opt-in OAuth helper](#721-oauth-for-mcp-over-http) when enabled on `/mcp`. The [MCP authorization reference](../../../../docs/mcp.md#auth-handling) covers the protocol details and upstream proposals.

- The tested harnesses handle sign-in with the authorization server and refresh when it issues a refresh token. Argsbarg need not run a login or consent flow, issue tokens, or store refresh tokens. Stdio and in-process CLI calls still use their local credential source; stdio has no standard MCP sign-in or refresh method.
- The HTTP resource server publishes Protected Resource Metadata for the public MCP URL. A missing or invalid token gets an HTTP `401` with a `WWW-Authenticate` bearer challenge that points to the metadata. The harness discovers the issuer, obtains an access token, and retries with `Authorization: Bearer <access-token>`. Insufficient token scope gets `403` with an `insufficient_scope` challenge and the required scope where step-up is supported.
- Verify the token's issuer, expiry, and intended audience before protected dispatch. Pass the verified caller to app guards and task providers for operation and ownership checks. Complete guard evaluation before opening a `200 text/event-stream` response so an `insufficient_scope` denial from a tool guard still returns HTTP `403` with `WWW-Authenticate`. A valid token for `/mcp` grants no automatic access to `/api` or `/rpc`, even on the same listener, and `/mcp` OAuth middleware does not run for `stdio` or `myapp mcp call`. Missing HTTP credentials never fall back to process env.

### MCP task providers

| MCP owns | App provider owns |
| --- | --- |
| Capability advertisement and client capability checks | Deciding whether to run inline or start background work |
| Encoding a tool's task reference and validating task messages | Task IDs, state, progress, results, errors, and persistence |
| Dispatching `tasks/get`, `tasks/update`, and `tasks/cancel` with caller context | Checking ownership on each operation, handling input, and deciding cancellation behavior |
| Mapping supported task updates to notifications when exposed | Producing state changes and deciding what survives restart |

Without a provider there is no advertised task capability or registered task operation. A client that hasn't opted in must not receive a reference; the tool chooses an inline result or clear error before starting work that requires task support. `tasks/get` carries terminal result or error; don't add native MCP list/result methods. Keep ordinary multi-round-trip input separate from task execution. The adapter validates input messages; the provider owns stored task-bound input and continuation state.

Apps can expose providers over app-owned CLI or HTTP operations, including HTTP `202` with a status URL. No bundled task engine, queue, worker, scheduler, store adapter, priority or retry policy, SQL endpoint, or admin surface. Apps implement and guard their own reporting, bulk retry, and other administrative operations.

The [background task scenarios](../../../../docs/use-cases/tasks.md) must work without custom JSON-RPC or framework internals.
