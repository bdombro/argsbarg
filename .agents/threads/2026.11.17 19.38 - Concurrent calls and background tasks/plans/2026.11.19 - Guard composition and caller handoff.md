# Guard composition and caller handoff (open 3.3 / 7.1 decision)

Disposition: resolved by accepted D90 and implemented in v9. This note remains as rationale and
option history, not an open decision.

This note breaks down the remaining open design choices for how transport auth (`mcp.http.oauth` / `mcp.http.middleware`), surface-level default guards (`cli.guard`, `http.guard`, `jsonRpc.guard`, `mcp.guard`), per-operation guards, and MCP task providers compose and pass typed `locals` (`caller`, etc.) at runtime and in TypeScript.

## What is already settled (with quotations)

From [7.1 App model, composition, and lifecycle](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#71-app-model-composition-and-lifecycle):

> Each surface (`cli`, `http`, `jsonRpc`, `mcp`) accepts an optional default `guard`; per-operation guards can supplement it (running after the default and receiving its `locals`) or explicitly replace it. Replacing the default does not disable transport or mount checks.

From [7.19 MCP transport adapters](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#719-mcp-transport-adapters):

> Attach middleware directly to the MCP HTTP mount. It can return an HTTP denial before dispatch or pass a verified caller to MCP tool guards and task providers. It doesn't apply to stdio, `/api`, or `/rpc`.

From [7.21 OAuth for MCP over HTTP](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#721-oauth-for-mcp-over-http):

> To make that possible, the `/mcp` HTTP adapter must finish running mount and tool guards *before* starting a `200 text/event-stream` response; once SSE streaming begins, an HTTP `403` challenge can no longer be sent.
>
> Because `mcp.http.oauth` runs only on `/mcp`, a tool that is also reachable via `stdio` or `myapp mcp call` won't receive an OAuth-verified caller on those local entry points. Those entry points need their own credential handling (via `mcp.guard` or the tool guard).

From [7.20 App-supplied task provider](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#720-app-supplied-task-provider):

> The provider verifies task ownership on every operation (`get`, `update`, `cancel`).

## Why this needs a crisp design (the 4 open questions)

With plain HTTP `/tools/{name}` removed, an MCP tool has three entry points: `/mcp` (HTTP), `stdio`, and `myapp mcp call`. Meanwhile, an HTTP route has `/api` and `myapp api`, and a JSON-RPC method has `/rpc` and `myapp rpc`.

That leaves four concrete questions to settle so the runtime behavior and TypeScript types stay simple.

### Question 1: How does a per-operation guard supplement vs override the surface default?

Suppose `http.guard` is `requireUser` (which populates `locals.caller`), and an app has:
1. A normal route (`GET /workspaces`) — inherits `http.guard`.
2. An admin route (`DELETE /workspaces/:id`) — wants `http.guard` **plus** `requireAdmin` (supplement).
3. A public route (`POST /webhooks/stripe` or `POST /login`) — wants to **bypass** `http.guard` (override with none, or override with `verifyStripeSignature`).

Compare the two cleanest API shapes:

```typescript
// Option 1A: `guard` supplements by default; `overrideGuard` (or `public: true`) replaces the surface default
http: {
  guard: requireUser,
  routes: [
    // Inherits `requireUser` -> handler gets `locals.caller`
    { method: "GET", path: "/workspaces", handler: ({ locals }) => /* ... */ },

    // Supplements `requireUser` -> runs `requireUser`, then `requireAdmin` (which receives `locals.caller`)
    { method: "DELETE", path: "/workspaces/:id", guard: requireAdmin, handler: ({ locals }) => /* ... */ },

    // Overrides surface default -> skips `requireUser`, runs only `verifyStripeSignature`
    { method: "POST", path: "/webhooks/stripe", guard: { mode: "override", run: verifyStripeSignature }, handler: ({ locals }) => /* ... */ },

    // Explicitly public -> skips `requireUser`
    { method: "POST", path: "/login", guard: "public", handler: () => /* ... */ },
  ],
}
```

```typescript
// Option 1B: `guard` always replaces the surface default; supplement by passing an array `[requireUser, requireAdmin]`
http: {
  guard: requireUser,
  routes: [
    // Inherits `requireUser`
    { method: "GET", path: "/workspaces", handler: ({ locals }) => /* ... */ },

    // Replaces default with a chain (explicit, zero magic)
    { method: "DELETE", path: "/workspaces/:id", guard: [requireUser, requireAdmin], handler: ({ locals }) => /* ... */ },

    // Replaces default with a single different guard
    { method: "POST", path: "/webhooks/stripe", guard: verifyStripeSignature, handler: ({ locals }) => /* ... */ },

    // Replaces default with none
    { method: "POST", path: "/login", guard: null, handler: () => /* ... */ },
  ],
}
```

**Tradeoff:**
- **1A** makes the most common case (surface auth + extra per-op check like `requireAdmin` or scope check) concise and safe by default — you can't accidentally drop authentication when adding an authorization check!
- **1B** has only one mental rule ("operation `guard` overrides surface `guard`"), at the cost of repeating `requireUser` in `[requireUser, requireAdmin]` — and forgetting to include `requireUser` silently drops authentication.

### Question 2: How does `/mcp` OAuth hand a verified `caller` to `mcp.guard`, tool guards, and `mcp.tasks`?

Look at the two layers on `/mcp`:
1. **Transport layer (`mcp.http.oauth` or `mcp.http.middleware`):** Runs *only* on `/mcp` HTTP requests. Verifies the Bearer token and produces a `caller` (e.g., `{ sub, scopes }`).
2. **Surface/operation layer (`mcp.guard`, `tool.guard`, `mcp.tasks`):** Runs on `/mcp`, `stdio`, and `myapp mcp call`.

Here is the exact tension if an app enables **both** `mcp.stdio: true` and `mcp.http: { oauth: ... }`:

```typescript
mcp: {
  stdio: true,
  http: {
    oauth: {
      resource: "https://reports.example/mcp",
      authorizationServers: ["https://auth.example"],
      verifyToken: (token, signal) => verifyOAuthJwt(token, signal), // returns { sub, scopes }
    },
  },
  // On `/mcp`, oauth already ran and verified the caller.
  // On `stdio` or `myapp mcp call`, oauth did NOT run!
  guard: async (ctx) => {
    if (ctx.locals.caller) return true; // already verified by `/mcp` oauth
    if (ctx.source !== "local") return deny("Verified caller required");
    // Local stdio / `myapp mcp call` credential:
    const token = ctx.env.get("REPORT_TOKEN");
    const caller = token ? await verifyLocalToken(token) : undefined;
    return caller ? allow({ caller }) : deny("REPORT_TOKEN required");
  },
  tasks: {
    // Task operations run on `tasks/get`, `tasks/update`, `tasks/cancel` (NOT `tools/call`).
    // They need the SAME verified `locals.caller` produced by `oauth` + `mcp.guard`!
    get: ({ taskId, locals, signal }) => repo.get(taskId, locals.caller, signal),
    cancel: ({ taskId, locals, signal }) => repo.cancel(taskId, locals.caller, signal),
  },
  tools: [
    {
      name: "export_report",
      // Runs AFTER `mcp.http.oauth` and `mcp.guard`, BEFORE SSE stream opens:
      guard: ({ locals }) =>
        locals.caller.scopes.includes("reports:export")
          ? true
          : deny("Missing reports:export scope", {
              oauth: { error: "insufficient_scope", scope: "reports:export" },
            }),
      handler: ({ inputs, locals, task, signal }) => /* ... */,
    },
  ],
}
```

**Notice two key details this snippet reveals:**
1. **`mcp.http.oauth` should write its verified result into `locals`** (e.g., `locals.caller` or whatever object `verifyToken` returns) **before** `mcp.guard` runs, so `mcp.guard`, `tool.guard`, `tool.handler`, and `mcp.tasks.*` all read from the exact same `locals` object.
2. **`mcp.guard` must also run before `mcp.tasks.{get,update,cancel}`** (not just `tools/call`), so task ownership checks receive the same `locals.caller` on both `/mcp` and `stdio`.
3. **For `/mcp`-only apps (`stdio: false`),** `mcp.guard` isn't even needed unless you want extra cross-tool checks — `mcp.http.oauth` populates `locals` directly for `tool.guard`, `tool.handler`, and `mcp.tasks`.

### Question 3: How does TypeScript infer `locals` across layers without casting?

In a plain nested object literal `argsbarg({ http: { guard, routes } })`, TypeScript **cannot** infer the return type of `http.guard` and feed it into sibling properties `routes[i].handler` unless either:

1. **Option 3A — Surface helper functions (`defineHttp`, `defineMcp`, `defineJsonRpc`, `defineCli`):**
   TypeScript *does* infer generic `TGuardLocals` across sibling properties of a single generic function call (`defineHttp({ guard, routes })`) when `routes` is typed against `TGuardLocals` (or `NoInfer<TGuardLocals>`):
   ```typescript
   http: defineHttp({
     guard: requireUser, // infers TLocals = { caller: User }
     routes: [
       {
         method: "GET",
         path: "/workspaces",
         handler: ({ locals }) => db.list(locals.caller), // `locals.caller` is typed as `User`!
       },
     ],
   })
   ```
   (Even better: `argsbarg(...)` itself can have generic parameters `TCliLocals`, `THttpLocals`, `TJsonRpcLocals`, `TMcpLocals` so inline blocks work with zero wrapper helper, AND `defineHttp(...)` / `defineMcp(...)` work when extracting a surface to its own file!)

2. **Option 3B — Explicit generic on extracted routes/tools:**
   When a route or tool lives in a separate file (`routes/workspaces.ts`), it doesn't sit inside `argsbarg(...)`. A tiny `route<AppLocals>({ ... })` or `tool<AppLocals>({ ... })` helper (same pattern as 8.x's `command({ ... })`) gives full type safety for extracted operations.

### Question 4: Structured denial shape across surfaces

A guard callback may return `true` to allow without adding locals, or `false` for a default denial. Use `allow({ caller })` to pass verified locals and `deny(...)` for a specific denial. The exact denial fields remain open.

One alternative is for `requireReporter` to build a raw HTTP `Response`:

```typescript
return {
  kind: "deny" as const,
  message: "Reporter credential required",
  http: new Response("Reporter credential required", {
    status: 401,
    headers: { "WWW-Authenticate": "Bearer" },
  }),
};
```

That gets awkward when a tool guard needs to trigger an OAuth `403 insufficient_scope` step-up challenge on `/mcp` while still rendering cleanly on `stdio` or `myapp mcp call`. Compare a structured denial:

```typescript
// Shared guard denial — each surface encodes natively
return deny("Missing reports:export scope", {
  code: "INSUFFICIENT_SCOPE",
  httpStatus: 403,
  oauth: { error: "insufficient_scope", scope: "reports:export" },
});
```

- **REST (`/api`):** returns HTTP `403` JSON error (or honors an optional raw `response` override if the app wants custom HTML/headers).
- **JSON-RPC (`/rpc`):** returns a JSON-RPC error object for that call (leaving other batch items untouched).
- **MCP HTTP (`/mcp`):** because guards run *before* SSE starts, emits HTTP `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="reports:export", resource_metadata="..."`.
- **MCP stdio / CLI:** returns a tool error (`isError: true`) or writes to stderr with a non-zero exit code.

## Recommended defaults (to confirm or adjust)

1. **Supplement by default (Option 1A):** Per-operation `guard` runs *after* the surface default `guard` and merges its `locals`; use `guard: "public"` or `guard: { mode: "override", run: ... }` to bypass/replace the surface default.
2. **Unified `locals` pipeline on MCP:** `mcp.http.oauth` (or `mcp.http.middleware`) establishes caller identity only on HTTP. `mcp.guard` and the tool guard also run for `myapp mcp call` and stdio under the same composition rules. Protected local calls still need a verified caller. On `/mcp`, finish guard evaluation *before* opening SSE.
3. **Inference on `argsbarg(...)` + optional `route()` / `tool()` helpers** for files extracted outside the root call. A handler gets a required `locals.caller` only when every enabled path that reaches it establishes one.
4. **Structured `deny(message, { code?, httpStatus?, headers?, oauth?, response? })`** so shared guards don't have to construct raw `Response` objects unless they want to.
