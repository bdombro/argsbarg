# D91 — Build-time keyed child composition

Status: ✅ accepted for the v9 child-composition implementation

Progress: ✅ decided

## Request and context

Task 91 settles the last public child-mount contract: the keyed build-time
descriptor, public namespaces, scoped credential views, guard and hook behavior,
startup collisions, exposure, and the implementation handoff.

D2 fixes the invocation boundary and already requires one exclusive `NameView`
source. D35 fixes the generated local mirrors and explicit relays. The seed and
architecture fix one executable, fixed catalogs, parent-owned transports, no
runtime bundle loader, no child lifecycle merge, and no implicit credential
forwarding.

- Asking task: task 91.
- Affected implementation: the future child-composition owner and its tests,
  public exports, examples and documentation.
- Evidence: architecture rev 2, D2 task 2, accepted task 35/D35, the seed's 7.1,
  7.22 and invocation-context rules, the child/gateway/guard design notes,
  `docs/use-cases/child-apps.md`, `docs/use-cases/gateway.md`, and the current
  factory plus HTTP, JSON-RPC and MCP catalogs/registries.
- Constraint: build-time composition only. No runtime imports, gateway registry,
  child `run()`, listener, lifecycle, store, OAuth or task-store merge.

## Options

- ✅ Mount immutable `App` definitions by key, copy their registered
  declarations into one parent-owned catalog snapshot, and derive every public
  name and source prefix from the mount-key path. This reuses the existing
  declaration, guard and dispatch machinery.
- 🚫 Import paths or prebuilt bundles at runtime. Rejected by the selected
  no-gateway/no-global-registry design and by the child's app-owned cleanup
  contract.
- 🚫 Forward an entire raw `process.env` or `Headers` object to a child. Rejected:
  prefix-only lookup is the child trust boundary and a broad source would permit
  sibling and unprefixed credentials.
- 🚫 Apply the parent's surface defaults or hooks to child declarations. Rejected:
  they are policy for the parent's own declarations, while the mounted child
  already has a compiled D2 guard plan and invocation lifecycle.
- 🚫 Make `children` a protocol gateway. Rejected: curated upstream gateways
  remain explicit operations with checked-in Zod contracts and app-owned
  clients. Child mounts are same-process declarations, not federation.

## Decider outcome

### Public descriptor

Add these public authoring types:

```ts
export type ChildSurface = "cli" | "http" | "jsonRpc" | "mcp";

export interface ChildAppMount {
  readonly app: App;
  readonly expose?: readonly ChildSurface[];
}

type AppSpecFields = {
  // existing fields
  readonly children?: Readonly<Record<string, ChildAppMount>>;
};
```

`children` is keyed at `argsbarg(...)` build time:

```ts
const app = argsbarg({
  ...suiteMetadata,
  children: {
    billing: { app: billingApp },
    reports: { app: reportsApp, expose: ["cli", "mcp"] },
  },
});
```

The object form is required; there is no direct-`App` shorthand, alias field,
runtime path form, or prefix override. A mounted child's public declarations,
guards and hook registrations are snapshotted once while the parent `App` is
constructed. Later mutation of the child spec does not change the parent.

Mount keys must match:

```text
^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$
```

Keys are exact and case-sensitive. Leading/trailing separators, `_`, `.`,
uppercase letters and `--` separators are invalid. Runtime JavaScript is checked
with the same rule.

`expose` is optional:

- Omitted means every surface actually configured in the child's composed
  snapshot, including valid descendants.
- Present means exactly that non-empty, duplicate-free subset.
- Requesting a surface that the child snapshot does not configure is a startup
  error, not a silent no-op.
- A parent's omitted/excluded surface cannot broaden a child's own mount
  exclusions. Effective exposure is intersection along a nested mount path.
- An exposed surface contributes only entries that the child's declaration
  already exposes. A declaration's existing `hidden` behavior is preserved;
  `cli.enabled: false` remains unregistered.
- `expose` never masks, filters or renames individual operations and is not a
  per-caller discovery mechanism.

### Namespace composition

For a child mounted on key path `K = [k1, k2, ...]`, compose each native public
name as follows:

| Surface | Child declaration `n` | Composed public identity |
| --- | --- | --- |
| CLI | command at child root/path | command path `k1 k2 ...` followed by the child's authored command path |
| REST | route `p` with id `n` | path `/${K.join("/")}${p === "/" ? "" : p}` and operation id `${K.join("__")}__${n}` |
| JSON-RPC | method `n` | `${K.join(".")}.${n}` |
| MCP | tool `n` | `${K.join("__")}__${n}` |

Examples:

- `billing` + route `/invoices` -> `POST /api/billing/invoices`.
- `billing` + route id `listInvoices` -> `billing__listInvoices`.
- `billing` + RPC method `reports.get` -> `billing.reports.get`.
- `billing` + MCP tool `list_invoices` -> `billing__list_invoices`.
- `operations` -> `billing` nested child -> tool `retry` becomes
  `operations__billing__retry`.

The child app's own root `key` is never publicized or used for identity. The
mount key is the sole namespace. A runnable child root becomes the CLI mount
leaf named by the final mount key. A grouped child root becomes the group named
by that key; its description/options/group metadata and child paths are
preserved. Parent-generated `api`, `rpc` and `mcp call` commands target the
composed catalogs, so no second child-specific mirror is created.

Nested `App` composition is supported. The outer key path prefixes every
declaration from the child snapshot. Runtime registration is nevertheless
flat: adapters and discovery see one immutable catalog, not child routers at
request time.

### Scoped source views

Source scoping is derived, not configurable.

For key path `billing/reports`:

```text
env name prefix    BILLING_REPORTS_
header name prefix billing-reports-
```

Rules:

- Environment segments are uppercased and joined with `_`, then receive a
  trailing `_`.
- Header segments retain the lowercase mount keys joined with `-`, then receive
  a trailing `-`. Header lookup remains case-insensitive because the backing
  HTTP `NameView` is case-insensitive.
- For a mounted child declaration, `ctx.env.get("TOKEN")` reads exactly
  `BILLING_REPORTS_TOKEN`; `ctx.headers.get("Authorization")` reads exactly
  `billing-reports-Authorization`.
- The wrapper never enumerates, copies, serializes or exposes the backing source.
  It returns `undefined` for missing values.
- There is no unprefixed lookup, sibling lookup, HTTP-to-env fallback, or
  env-to-header fallback.
- A parent child can read only its own source prefix. A declaration on
  `billing` may not discover a descendant `billing/reports` value by asking for
  `REPORTS_TOKEN`: the wrapper reserves descendant mount prefixes and returns
  `undefined` for those names. Invocation of `reports` receives the full nested
  prefix.
- Startup configuration is outside `InvocationContext` and remains app-owned;
  mounting does not scope code that directly reads `process.env` outside
  declarations.

At the same sibling level, source prefixes must not overlap. For example, keys
`billing` and `billing-reports` conflict because `BILLING_` is a prefix of
`BILLING_REPORTS_` and `billing-` is a prefix of `billing-reports-`. Reject the
collision regardless of currently exposed surfaces. Parent/child nesting is
allowed because descendant-prefix lookups are explicitly hidden from the
ancestor view as described above.

Parent OAuth/transport middleware may establish verified `locals` at the suite
boundary, but it does not make the suite's raw `Authorization` header available
to a child. A child's conventional local credential is the scoped
`Billing-Authorization`/`BILLING_TOKEN` source. A child guard may instead consume
verified mount locals produced by app-owned middleware.

### Guard, hook and task-callback propagation

Mounted declarations retain their already-compiled D2 `BoundDeclaration`.
Composition changes only native lookup names and the call's source view. It does
not copy or rebuild the child plan.

For one child invocation, order is:

1. parent transport/mount admission, if configured, may deny or seed fresh
   locals;
2. the child's own surface default;
3. the child's own operation supplement/override/public selection;
4. the child's handler.

The parent app's own surface default guard and invocation hooks do not apply to
mounted child declarations. Parent policy that must cover every declaration
belongs at the transport/mount layer or must be included by the child
declarations themselves. No child-mount `guard` field is added in v9; it would
duplicate the accepted guard compiler without supplying a sound typed-locals
relationship.

Locals are freshly copied for every invocation. Mount-seeded values are available
to child guards, and child `allow({ ... })` additions continue through to the
handler. A guard result, denial, source view, signal, caller and captured output
never leak to another child or call. Child declaration hooks and child error
reporters remain attached to that declaration and run once. Parent wire
middleware/hooks observe the parent-owned transport only.

MCP task providers and task stores are not currently implemented, and this
decision does not authorize their implementation. When task callbacks are
added, a child task follow-up must resolve the original composed child
registration, establish a new caller from the **current** request/transport,
build the same scoped child `NameView`, rerun the applicable child MCP guard plan,
and then perform ownership and grant checks in the app-owned provider. It must
not reuse the original request's credentials or skip child policy. A provider
belongs to the child app; stores, leases, IDs and lifecycle are never merged
automatically. The later task-provider decision owns its opaque-reference and
routing wire format.

### Collisions and startup failure

`argsbarg(...)` validates the complete composed snapshot before returning.
Registration order never resolves ambiguity.

Reject:

- invalid mount keys;
- duplicate or overlapping sibling source-prefix claims;
- duplicate final CLI paths, including parent commands, built-ins and generated
  `api`/`rpc`/`mcp` commands;
- duplicate REST operation ids;
- overlapping REST method/path claims after path composition;
- duplicate JSON-RPC method names;
- duplicate MCP tool names;
- an `expose` entry that is duplicated or targets an unconfigured child
  surface;
- any composed JSON-RPC name rejected by the existing method-name profile;
- any composed MCP name rejected by the existing tool profile.

Identical unnamespaced declaration names are legal when different mount-key
paths make their final public identities unique. A collision error names the
surface, final public identity, and the two owner paths. A hidden declaration
still claims dispatch identity and therefore still collides with a visible one.
No entry is silently dropped, renamed, shadowed or resolved by insertion order.

### Transport and lifecycle ownership

Only the parent `App` starts transports:

- a composed REST route contributes to the parent's `/api` catalog;
- a composed method contributes to the parent's `/rpc` catalog;
- a composed tool contributes to the parent's `/mcp` stdio/HTTP registry;
- child CLI declarations contribute to the parent's CLI tree and discovery.

The parent owns one listener, service selection, MCP transport selection,
server identity, wire instructions, OAuth admission, discovery documents,
shutdown and readiness. Child listener settings, host/port, service
instructions, OAuth configuration, packaging metadata and lifecycle callbacks
are not merged. A child-only HTTP/RPC/MCP surface is sufficient to make that
service configured on the parent.

The child object's `run()`, `serveHttp()` and `serveMcp()` are never called.
There is no dynamic import, startup path loading, `globalThis` registry, bundle
contract, fallback to separate processes, or runtime gateway loader. Resources
captured by child handlers are owned and closed by the executable that created
the child declarations.

## Acceptance summary

The parent gets one fixed executable and one catalog per configured native
surface. Children are build-time keyed snapshots, not runtime apps. Their public
names are composed deterministically, their sources are prefix-isolated, their
guards stay intact, exposure is fixed at startup, and collisions fail closed.
