# D90 — CLI and MCP guard and caller-seed APIs

Status: ✅ accepted for implementation planning

Progress: ✅ decided

## Request and context

Task 90 settles the public CLI/MCP guard declarations and the MCP caller-seed
handoff left by DP-20 and D2. It does not change REST/JSON-RPC behavior,
the D2 invocation context, the D35 mirror commands, discovery catalogs, native
results, credential-source separation or the fixed MCP transport selection.

- References: D2 task 2, DP-20 task 30, D35, tasks 35/36 and the guard
  handoff note; current `src/core/types.ts`, `src/core/invocation.ts`,
  `src/runtime/{cli,invoke}.ts`, and `src/mcp/{registry,dispatcher,http,stdio}.ts`.
- Constraint: read-only decision. No source, test, network or host work.
- Scope: declarations, guard order, MCP HTTP admission, typed seed passage,
  public/internal ownership and focused acceptance coverage.

## Authority and evidence

D2 owns the shared `Guard`, `OperationGuard`, `InvocationSource`,
`InvocationBase`, `CompiledGuard`, `InvocationOutcome` and guard order. DP-20
owns direct `InvocationContext` CLI handlers and deliberately deferred public
CLI guards. D35 owns the generated local mirror/relay behavior and forbids
relay-local fallback or ambient credential forwarding. REST and JSON-RPC
already implement the D2 supplement/override/public composition and remain
authoritative references.

The current code confirms the two gaps:

1. `RunnableCommand`, `McpToolSpec` and `McpAppConfig` do not expose operation
   or surface guards; CLI and MCP registration currently compile empty plans.
2. `McpHttp` accepts three package-internal aliases (`admission`, `admit`,
   `middleware`) and lets admission return a bare seed, while the public
   factory does not expose that middleware. HTTP seed locals therefore do not
   have one accepted public name or result shape.

## Options

- ✅ Add one optional CLI policy block, `cli.guard`, one command operation
  `guard`, one MCP policy `mcp.guard`, one tool operation `guard`, and one
  exact `mcp.http.middleware` seed callback. All use D2's existing
  `OperationGuard` composition.
- 🚫 Put a CLI default guard on the runnable root. That makes one property
  mean both surface policy and operation policy for a one-command app.
- 🚫 Give middleware, admission and seed three aliases or a bare
  `Response | Seed` result. Aliases drift, and a bare object cannot
  distinguish author mistakes from a terminal HTTP response.
- 🚫 Add public stdio/local caller callbacks that pre-read process
  environment. That would duplicate `InvocationSource` and move policy into
  transport code.
- 🚫 Infer generated `api`/`rpc`/`mcp call` through the CLI guard. A mirror
  invokes its declared target surface, not a synthetic CLI operation.

## Decider outcome

### Public declaration surface

Keep DP-20's existing root CLI command shape. Add a narrowly scoped surface
configuration block; do not move existing root `commands` into it:

```ts
argsbarg({
  commands: [
    command({
      key: "report",
      guard: requireWorkspace,
      handler: ({ inputs, locals }) => {
        // ...
      },
    }),
  ],
  cli: {
    guard: requireLocalCaller,
  },
  mcp: {
    guard: requireMcpCaller,
    http: {
      middleware: establishHttpMcpCaller,
    },
    tools: [
      tool<ReportLocals>()({
        name: "generate_report",
        guard: requireReportScope,
        inputSchema: ReportInput,
        handler: ({ inputs, locals }) => {
          // ...
        },
      }),
    ],
  },
  // ...
});
```

The exact author-facing additions are:

```ts
interface CliAppConfig<Seed extends object = Locals> {
  readonly guard?: Guard<unknown, Seed, object>;
}

interface AppSpecFields {
  readonly cli?: CliAppConfig<Locals>;
}

type RunnableCommand /* existing fields */ = {
  readonly guard?: OperationGuard<Guard<ParsedCommandInput, Locals, object>>;
  // existing handler and declaration fields
};

interface McpAppConfig<Seed extends object = Locals> {
  readonly tools: readonly McpToolRegistration<Seed>[];
  readonly guard?: Guard<unknown, Seed, object>;
  readonly http?: McpHttpConfig<Seed>;
  // existing instructions and packaging fields
}

interface McpToolSpec<Seed extends object, InputSchema, Result> {
  readonly guard?: OperationGuard<
    Guard<z.output<InputSchema>, Seed, object>
  >;
  // existing fields and direct handler
}
```

`command(...)` remains the ordinary builder and extracted code may continue
to use the augmented public `Locals` type. Implement an explicit
`command<Seed>()(spec)` extracted form, parallel to `route<Seed>()` and
`tool<Seed>()`, if the concrete TypeScript implementation cannot otherwise
express operation-added locals without widening. The one-call
`command(spec)` form remains valid with `Locals`.

The `guard` callback is a normal D2 `Guard`; it is not an app hook. `guard`
sees parsed `inputs`, the current source and fresh seed locals. It receives no
transport response object, raw argv, raw request body or synthetic headers.

### Composition and applicability

Every user-authored CLI leaf compiles this plan:

1. `cli.guard`, if configured;
2. the command's `guard`, if it is a supplement.

`command.guard: { mode: "override", run }` replaces only `cli.guard`.
`command.guard: "public"` removes only the CLI surface guard. Neither can
bypass a later transport admission check because CLI has no MCP/HTTP admission
middleware.

Every `tools/call` compiles this plan:

1. MCP mount/admission middleware, which completes before D2 dispatch;
2. `mcp.guard`, if configured;
3. the tool's `guard`, if it is a supplement.

`tool.guard: { mode: "override", run }` replaces only `mcp.guard`.
`tool.guard: "public"` removes only the MCP surface guard. Neither bypasses
`mcp.http.middleware`.

The MCP surface/tool plan runs on:

- native MCP HTTP `tools/call`;
- MCP stdio `tools/call`;
- local `mcp call` generated by D35.

It does not run for `server/discover` or `tools/list`, because those are
fixed-catalog protocol reads and never invoke an operation. Mount middleware
still runs on those HTTP requests when configured, as an `/mcp` transport
policy.

The CLI surface plan applies only to user-authored CLI leaves. D35-generated
`api`, `rpc` and `mcp call` invoke their target REST, JSON-RPC or MCP
declaration and run that target's surface and operation plan. Do not run both
CLI and target policy, and do not add generated-command operation guards.

Relay calls perform no local guard plan. The destination server performs its
own middleware, surface guard and operation guard. A relay failure never
falls through to the local declaration.

### MCP HTTP caller seed

Expose exactly one mount policy name:

```ts
interface McpHttpMiddlewareContext {
  readonly method: string;
  readonly name?: string;
  readonly headers: NameView;
}

type McpHttpMiddlewareResult<Seed extends object> =
  | { readonly kind: "respond"; readonly response: Response }
  | { readonly kind: "next"; readonly locals: Seed };

type McpHttpMiddleware<Seed extends object> = (
  request: Request,
  context: McpHttpMiddlewareContext,
) => MaybePromise<McpHttpMiddlewareResult<Seed>>;

interface McpHttpConfig<Seed extends object = Locals> {
  readonly middleware?: McpHttpMiddleware<Seed>;
}
```

`request` exists only at this transport boundary. Middleware verifies HTTP
credentials and returns fresh request-local verified locals. It receives the
case-insensitive header `NameView`, `Mcp-Method` and optional `Mcp-Name`
before body consumption. The callback never receives `process.env`.

`{ kind: "respond", response }` ends that HTTP request without body decode,
guard or dispatcher work. `{ kind: "next", locals }` contributes the seed
locals. Reject a return value that is neither branch as an internal server
response. Do not retain caller objects after the request.

Remove the package-internal `admission` and `admit` aliases. `middleware` is
the single public and internal spelling.

The HTTP adapter must create:

```ts
InvocationBase<Seed> = {
  source: "http",
  headers,
  locals: frameworkSeed merged with middleware.locals,
  signal: exact linked request signal,
  surface: "mcp",
};
```

The merged seed is passed unchanged in meaning to `dispatchMcpRequest` and
then cloned once by `invokeBound`, where D2 guard locals evolve. Framework
fields such as `requestId` and `reportProgress` remain runtime-owned; app
middleware may not replace framework progress transport behavior. A handler
must receive verified caller data only through final `locals`, not through
raw request objects or the header view after middleware.

When middleware is omitted, the seed contains only framework locals. Public
tools remain possible; an app that requires a caller must enforce and
establish it in the shared MCP surface/operation guard plan.

### Local MCP callers and required-caller contract

There is deliberately no public `mcp.stdio.seedLocals` or
`mcp.local.seedLocals` callback.

- Stdio constructs one fresh framework seed per request and exposes only the
  process-local `env` `NameView`.
- D35 local `mcp call` constructs one fresh framework seed and the same
  local-source `env` view.
- `mcp.guard` or a tool supplement must verify local credentials and return
  `allow({ caller })` when protected local entry points are enabled.

Thus all three paths share one required-caller rule:

- HTTP middleware may pre-seed verified caller material, but the MCP guard
  plan still owns whether that caller is sufficient.
- Stdio and local mirror have no HTTP middleware shortcut; they must derive
  their caller from the exclusive local source.
- A declaration typed to require `locals.caller` requires every enabled
  entry point to establish it. Startup must not synthesize a fallback from
  env on HTTP or from HTTP headers on local calls. A missing/invalid caller is
  a denial, not an optional handler precondition.

This API uses an app-owned, not framework-defined, caller shape. `Locals` may
be module-augmented for the package root; extracted `tool<Seed>()` and
`command<Seed>()` builders provide narrower explicit seeds.

### MCP denial transport

The dispatcher must preserve D2 denial identity long enough for the MCP
transport adapter to choose native encoding. Its internal tool-call result
must carry:

```ts
interface McpRegisteredToolCall {
  readonly response: McpResultResponse | McpErrorResponse;
  readonly outcome: InvocationOutcome<unknown>;
  readonly stdout: string;
  readonly stderr: string;
}
```

Stdio and local mirror continue to present the complete native MCP response
from `response`.

HTTP treats an `outcome.kind === "denied"` with `denial.http` or
`denial.challenge` as an admission-complete, pre-SSE HTTP denial:

- status is `denial.http.status ?? 403`;
- `denial.http.headers` are copied;
- `denial.challenge` produces `WWW-Authenticate: Bearer …`;
- the JSON body is the safe D2 denial `{ error: { code, message } }`.

A denial with neither `http` nor `challenge` remains an MCP tool-error result
and is returned in the native MCP envelope. This preserves the ability to
use one guard over stdio, local and HTTP while making authentication denials
HTTP-native before SSE begins.

All guard work must finish before progress SSE can start. The HTTP adapter
already races first progress against terminal dispatch, but must suppress
guard denials with HTTP metadata from that race and emit the native HTTP
response once. This is a caller of the existing D2 outcome, not a change to
REST/RPC encoders.
