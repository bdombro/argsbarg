## Brief

Brief identity: task 22 contract rev 1 + accepted D2/DP-11

Implement an independent, transport-neutral JSON-RPC declaration/catalog and 2.0 codec over the accepted invocation core. It must bind `params` directly to a method's Zod input, dispatch requests and independent batch members through `invokeBound`, emit only JSON-safe values, and generate OpenRPC from the same fixed method catalog. HTTP mounting, the public factory extension, root exports, listener lifecycle, and the CLI `rpc` mirror are explicit handoffs; none may be inferred from REST or MCP declarations.

Status: 🔄 review; `decided: DP-22` unblocks implementation within the five-file JSON-RPC leaf

### Why and canonical context

- The settled v9 design makes `jsonRpc` a first-class optional surface. Apps explicitly declare named methods, input/output schemas, handlers and guards; REST routes and MCP tools do not generate RPC methods.
- D2 makes the shared boundary non-negotiable: a binder supplies native `rawInputs`, `InvocationBase<Seed>` and one `BoundDeclaration`; `invokeBound` performs the sole Zod parse, runs the compiled D2 guard plan, captures output and returns exactly `ok`, `denied`, `invalid` or `error`.
- Existing 8.x JSON-RPC is MCP framing coupled to `mcp server.ts` and argv conversion in `headless/tool-call.ts`. It is prior art for envelope validation and recovery only, not a standalone catalog or public contract.
- The network adapter later mounts only `POST /rpc` and `GET /rpc/openrpc.json`; it owns body reading and HTTP status selection, not envelope decoding or authorization. The local mirror later reads one JSON `params` value from stdin, looks up the same registered method, and calls the shared method-invocation primitive with `source: "local"` and env-only credentials. Neither path fabricates argv or HTTP headers.
- `/api-rpc`, `/mcp-rpc`, `/mcp/openrpc.json`, `/tools/openapi.json`, inferred REST methods, and inferred MCP methods are exclusions, not deferred work.

### Observed current and target state

**Current.**

- `src/core/invocation.ts` provides `NameView`, `InvocationBase`, `BoundDeclaration`, `InvocationOutcome`, `Denial`, `AppError` companion behavior and `allow`/`deny`.
- `src/runtime/invoke.ts` runs one Zod parse, ordered guards and one handler, captures stdout/stderr per ALS scope, preserves thrown values and checks the supplied abort signal.
- `src/mcp/server.ts` contains line-oriented MCP JSON-RPC parsing and MCP-specific lifecycle/tool behavior. It is not reusable as a standalone `/rpc` dispatcher.
- `src/http/openapi.ts` demonstrates registry-derived discovery from a single collection, schema emission through `toJsonSchema`, and a pure generator. `src/http/server.ts` demonstrates request parsing and HTTP response adaptation but currently owns one HTTP tree-derived route model.
- No standalone JSON-RPC declaration, catalog, batch codec, OpenRPC generator, or local `rpc` mirror exists.

**Target.**

- A method is explicitly registered once and appears identically in lookup, dispatch and OpenRPC. Duplicate method names fail at catalog creation; lookup never falls through to CLI, REST or MCP.
- The wire decoder accepts one JSON-RPC 2.0 request/notification or a non-empty batch, preserves the `decided: DP-22` ID union exactly, rejects malformed envelopes before invocation, and binds the decided object/array `params` unchanged as `rawInputs`. It never coerces positional params into an object and never applies an MCP-style wrapper.
- A valid request invokes exactly one catalog method. A valid notification performs normal validation/guards/handler work but never emits a per-message response.
- A batch schedules each structurally valid member independently. One invalid, denied or failed member does not abort, authorize, or rewrite another. Each member gets fresh locals and a per-member signal linked to transport cancellation. Notification members produce no response, and an all-notification batch produces no dispatch body; the listener owns the final HTTP status.
- JSON-RPC request validation precedes shared input validation. Runner `invalid`, `denied`, `AppError` and unknown-error outcomes become native JSON-RPC error envelopes without exposing captured stdout/stderr, raw params, headers, env, causes, stacks or credentials. Handler results and `error.data` must be JSON-safe; an encoding failure becomes that member's Internal error, not a transport-wide failure.
- OpenRPC contains exactly the registered methods and their input/output schemas. The catalog and codec do not open a listener, read process env, start a server, or depend on MCP.

### Established behavior

1. **Catalog identity**
   - Method names are exact, case-sensitive strings in the registered catalog.
   - Input/output schemas belong to that method only; no inference from `http` route verbs/templates or MCP tool names.
   - The catalog is fixed after registration. Dispatch and OpenRPC use the same declaration array/lookup map, with stable registration order and no lazy mutation; guards do not remove discovery entries.
   - `decided: DP-22`: declared names are exact, case-sensitive, trimmed, non-empty strings; control characters are invalid and names beginning `rpc.` are reserved and rejected. Duplicate names reject startup/registration before any listener can expose a partial catalog.

2. **Envelope boundary**
   - `decided: DP-22`: exactly `"jsonrpc": "2.0"` is accepted; the only envelope members are `jsonrpc`, `method`, optional `params` and optional `id`. A request has a string `method`; unknown members, `result`, and `error` are Invalid Request.
   - Structural envelope errors are JSON-RPC errors, not runner `invalid` outcomes. They must not call schema parsing, guards or handlers.
   - `decided: DP-22`: an omitted `id` is a notification. Presence is tracked separately from value, so `0`, `""`, `null`, and finite fractional numbers are requests. Valid IDs are `string | number | null`; numbers must be finite. Invalid IDs make the request malformed and use `id: null` in the error.
   - The codec must distinguish invalid JSON from an invalid JSON value and must never parse a batch member through the MCP stdio line reader.

3. **Native params and invocation**
   - `params` is passed unchanged as `rawInputs`; no flattening, argv generation, query/body precedence or MCP `input` wrapper is applied.
   - `decided: DP-22`: omitted `params` remains `undefined`; object and array values pass unchanged; scalar/null `params` produce Invalid params and never reach Zod. The schema decides whether an otherwise structured value is valid.
   - HTTP calls use only `source: "http"` plus a case-insensitive header `NameView`; local CLI mirrors use only `source: "local"` plus env. Missing HTTP credentials never fall back to env.
   - Every member gets fresh seed locals, its own `AbortController`/signal linked to request cancellation and its own ALS output scope. Batch execution can overlap; `process.chdir` remains subject to the existing concurrent-call restriction. A member's local controller must not abort a sibling.

4. **Results and errors**
   - `decided: DP-22`: `ok` serializes the handler result directly as JSON-RPC `result`, with no MCP/REST/content envelope. A strict JSON-value check rejects `undefined`, non-finite numbers, bigint, holes, circular values, accessors, symbols/functions and non-plain objects; that request becomes Internal error. `outputSchema` remains declaration, return-type and discovery metadata; there is no runtime output-schema parse.
   - `denied` becomes the `decided: DP-22` `-32001` error with `{ kind: "denial", code }`; its message is the denial message. It does not affect neighboring batch members.
   - `invalid` becomes JSON-RPC `Invalid params`. Format the original `ZodError.issues` locally after the sole D2 parse, using path-prefixed messages and the same ten-issue bound as current schema validation; do not call `validateWithSchema` and parse twice.
   - An `AppError` becomes an application error with stable code/message and accepted JSON-safe details. Non-JSON `details` fail closed to the projection without exposing the raw value. Other thrown values become a generic Internal error; raw error objects, stacks, causes, headers, params and captured credentials must not cross the wire.
   - Captured stdout/stderr are never appended to a JSON-RPC response. They remain available to native encoders/diagnostics and are isolated by D2.

5. **Batches and notifications**
   - `decided: DP-22`: empty batches are one Invalid request envelope with `id: null`.
   - Each batch member is decoded, authorized and invoked independently. Batch response entries may be emitted in registration-independent execution order; the unit API must test by identity rather than assuming global completion order.
   - `decided: DP-22`: duplicate valid request IDs in one batch are invalid in every duplicated position, each producing Invalid request with that valid ID and never invoking a method. Unique members remain independent. Duplicate notification IDs do not exist because notifications omit `id`.
   - Notifications return no entry for method-not-found, invalid params, denial or handler failure. Malformed values that are not valid request/notification objects still get the protocol's Invalid request response.

6. **OpenRPC**
   - `generateOpenRpc(catalog, appInfo)` is pure and writes no files.
   - It emits app info plus one entry per fixed catalog method; dispatch and discovery cannot drift by independently walking another source.
   - Input/output are emitted from the declaration's Zod schemas with `toJsonSchema(..., "input"/"output")`; unknown schemas or unrepresentable output fail registration/document generation rather than being omitted silently. Recursive/local `$ref` policy is explicit and matches the accepted OpenRPC mapping rather than borrowing MCP root wrappers.
   - No REST paths, MCP methods, health endpoints or listener URLs are added to the OpenRPC document.

#### Public declaration and block

- Keep the root `argsbarg(...)` factory and expose one identity builder named `method` from the package's public root when the later root owner integrates it. The package-internal authored shape is:

```ts
type JsonRpcResultOf<OutputSchema> =
  OutputSchema extends z.ZodType ? z.output<OutputSchema> : unknown;

type JsonRpcMethodSpec<
  Locals extends object,
  InputSchema extends z.ZodType,
  OutputSchema extends z.ZodType | undefined,
> = {
  name: string;
  description: string;
  summary?: string;
  inputSchema: InputSchema;
  outputSchema?: OutputSchema;
  paramNames?: readonly string[];
  guard?: OperationGuard<Guard<z.output<InputSchema>, Locals, object>>;
  handler(
    context: InvocationContext<z.output<InputSchema>, Locals>,
  ): MaybePromise<JsonRpcResultOf<OutputSchema>>;
};

declare function method<Locals extends object = object>(): <
  const InputSchema extends z.ZodType,
  const OutputSchema extends z.ZodType | undefined = undefined,
>(
  spec: JsonRpcMethodSpec<Locals, InputSchema, OutputSchema>,
) => JsonRpcMethodSpec<Locals, InputSchema, OutputSchema>;
```

- `InputSchema` and `OutputSchema` infer context input and handler result from the declaration, not the surrounding array. Extracted methods call `method<Locals>()({ ... })`; the zero-argument first call fixes the concrete locals type while allowing the second call to infer schema/result types. Inline methods use `method()({ ... })`. Locals never widen to `any`/`unknown`; catalog compilation still checks the D2 guard-plan final locals. `NoInfer` preserves declaration-owned inference in heterogeneous arrays.
- `name`, `description`, `inputSchema`, and `handler` are required. `summary`, `outputSchema`, `paramNames`, and operation `guard` are optional. `paramNames` is legal only for a fixed tuple input root and is required there.
- The block is exactly `jsonRpc: { methods, guard? }`. Presence enables the surface; `enabled` is not a field. `methods` is fixed at catalog creation and every member must come from `method(...)`.
- Names are exact, case-sensitive, trimmed, non-empty strings with no control characters. `rpc.` is reserved and rejected, as is any duplicate. CLI, REST and MCP-only fields (`path`, `method`, `positionals`, `options`, `stdio`, `http`, etc.) are not part of the method type.

```ts
type ReportLocals = { caller: { id: string } };

const generateReport = method<ReportLocals>()({
  name: "reports.generate",
  description: "Generate one project report.",
  summary: "Generate report",
  inputSchema: z.strictObject({ projectId: z.string().min(1) }),
  outputSchema: z.strictObject({ projectId: z.string(), total: z.number() }),
  handler: ({ inputs, locals, signal }) =>
    generate({ projectId: inputs.projectId, caller: locals.caller, signal }),
});

const app = argsbarg({
  key: "reports",
  description: "Reports.",
  version: "1.0.0",
  jsonRpc: {
    guard: requireCaller,
    methods: [generateReport],
  },
});

method<ReportLocals>()({
  name: "bad-result",
  description: "Compile failure.",
  inputSchema: z.strictObject({}),
  outputSchema: z.strictObject({ total: z.number() }),
  // @ts-expect-error result must match the declared output schema
  handler: () => ({ total: "many" }),
});

method<ReportLocals>()({
  name: "bad-cross-surface-field",
  description: "Compile failure.",
  inputSchema: z.strictObject({}),
  // @ts-expect-error REST method belongs only to an HTTP route
  method: "POST",
  handler: () => ({}),
});

method<ReportLocals>()({
  name: "bad-param-shape",
  description: "Compile failure.",
  inputSchema: z.strictObject({ known: z.string() }),
  handler: ({ inputs }) => {
    // @ts-expect-error undeclared input is not inferred

  },

```

#### Envelope, IDs, params, batches, and notifications

- Only the four request members above are accepted. `params` may be an object or array; omitted stays `undefined`. Scalar, `null`, `1e400`-as-number-ID, boolean and object/array IDs do not reach Zod.
- A valid `id` is a string, finite JSON number (fractional allowed), or `null`; presence, not truthiness, determines a request. `-0` is accepted but JSON serialization normalizes it to `0`. Syntax invalid for JSON (`NaN`) is Parse error; overflow (`1e400`) becomes Invalid request with `id: null`.
- Duplicate valid IDs in a non-empty batch are classified as Invalid request at each duplicated position. All other members dispatch independently.
- Notifications are valid requests with no `id` member. They run lookup, validation, guards and handlers normally but always return no envelope, including failure. Malformed values are requests with Invalid request responses, not notifications.

| Fixture | Accepted/effect |
| --- | --- |
| `id: "r-1"`, `id: 0`, `id: ""`, `id: 1.5`, `id: null` | Accepted requests; response repeats the value |
| omitted `id` | Notification; no envelope |
| `id: true`, `id: {}`, `id: []`, `id: 1e400` | Rejected Invalid request, response `id: null` |
| `id: NaN` in source text | JSON Parse error, `id: null` |
| two batch members with `id: 7` | Both Invalid request, neither invokes |
| `params` object or array | Passed unchanged as `rawInputs` |
| omitted `params` | Passes `undefined` unchanged |
| scalar or `null` params | `-32602` Invalid params before Zod |
| array supplied to object schema | Reaches Zod unchanged, then `-32602` |
| extra envelope member | `-32600` Invalid request before Zod |

#### Errors, output safety, and observation

`decided: DP-22` fixes these encodings:

| `InvocationOutcome` / condition | JSON-RPC envelope |
| --- | --- |
| `ok` with strict JSON value | `result` exactly the handler value |
| `ok` with unsafe/non-serializable value | `-32603 Internal error` with no `data` |
| `invalid` | `-32602 Invalid params`, `data: { kind: "invalid-params", issues: string[] }` |
| `denied` | `-32001`, denial message, `data: { kind: "denial", code }` |
| `error` containing `AppError` with safe `details` | `-32000`, `AppError.message`, `data: { kind: "application", code, details? }` |
| `error` containing `AppError` with unsafe `details` | Same `-32000` application envelope, but omit `details` |
| Any other `error` | `-32603 Internal error` with no `data`, regardless of thrown text/cause |
| Invalid JSON | `-32700 Parse error`, `id: null` |
| Invalid envelope | `-32600 Invalid Request`, valid present ID or `id: null` |
| Unknown method | `-32601 Method not found` |

- Zod issue strings use the existing path-prefixed formatter, first 10 plus `…and N more errors`. `data` never contains the original issue input, raw params, cause, stack, captured stdout/stderr, env, headers, locals, `Denial.http`, or challenge metadata.
- `error.data` values and successful results accept the same strict JSON-value definition. For an `AppError`, unsafe `details` is omitted; it does not replace the stable application error with Internal error.
- A handler-thrown `AbortError` and cooperative cancellation use the generic `-32603` error for requests. Notifications observe it and still return no envelope.
- Notification outcomes are delivered to the listener's existing hooks/logging/observation path as bounded metadata (method, optional valid ID if applicable, outcome category, standard/application/denial code). They must never affect HTTP status: single and all-notification dispatch remain `204`; a mixed batch's response-bearing status stays `200`. One notification cannot rewrite a sibling response.

#### OpenRPC mapping and references

- Emit OpenRPC `1.3.2`, preserving catalog registration order.
- A method has `name`, `description`, optional `summary`, one `params` entry per representable input field/tuple slot, one `result`, and `errors: [-32700, -32600, -32601, -32602, -32603, -32001, -32000]` descriptors. The five standard messages are exact; denial/application descriptors use representative `Access denied`/`Application error` messages and actual calls retain app policy text.
- Object-rooted emitted input schemas use `paramStructure: "by-name"`; each `properties` entry becomes a `ContentDescriptor` with its property name, emitted schema and required bit from the root `required` array. The root must require `additionalProperties: false`.
- Fixed tuple-rooted schemas use `paramStructure: "by-position"`. `paramNames` must be present, unique, trimmed/non-empty and exactly as long as `prefixItems`; an index below `minItems` is required. Rest/variadic tuples and arbitrary `z.array(...)` roots are rejected at catalog creation because OpenRPC cannot name their unbounded slots.
- Non-object/non-tuple **input** roots, object input roots without `additionalProperties: false`, input unions, recursive/unresolved/external refs, transforms that cannot emit to JSON Schema, and any other non-representable shape are rejected at catalog creation rather than wrapped or silently omitted. Output roots may be scalar, array, object or union JSON Schema because OpenRPC places the result in one schema-bearing descriptor.
- Internally referenced acyclic `$defs`/`definitions` are dereferenced into each schema; unresolved/external/circular refs fail. `$schema`, `$id`, and emptied definition containers are removed after dereferencing. The same policy applies to input and output.
- `outputSchema` is emitted with `toJsonSchema(..., "output")`; without one, the required result descriptor uses unconstrained schema `{}`. Output schemas are never MCP-wrapped and are never runtime-parsed.

```json
{
  "name": "reports.get",
  "summary": "Get report",
  "description": "Read one generated project report.",
  "paramStructure": "by-name",
  "params": [
    {
      "name": "id",
      "required": true,
      "schema": { "type": "string", "minLength": 1 }
    }
  ],
  "result": {
    "name": "result",
    "schema": {
      "type": "object",
      "properties": {
        "id": { "type": "string" },
        "total": { "type": "number" }
      },
      "required": ["id", "total"],
      "additionalProperties": false
    }
  },
  "errors": [
    { "code": -32700, "message": "Parse error" },
    { "code": -32600, "message": "Invalid Request" },
    { "code": -32601, "message": "Method not found" },
    { "code": -32602, "message": "Invalid params" },
    { "code": -32603, "message": "Internal error" },
    { "code": -32001, "message": "Access denied" },
    { "code": -32000, "message": "Application error" }
  ]
}
```

**Rationale/rejections.** Object and tuple params match JSON-RPC's structured params while avoiding MCP's `{ input }` coercion. Standard-compatible `null` IDs and finite fractional numbers maximize protocol compatibility, while duplicate batch IDs are rejected to avoid ambiguous correlation. A strict envelope catches silent client typos. Separate `-32000`/`-32001` values preserve stable application-vs-denial categories without exposing D2 internals. Runtime output parsing is rejected as a D2 change and duplicates schema work; strict JSON safety is still required at the encoder. Notification failures remain observe-only because an HTTP error status with no protocol response would conflate independent members and leak dispatch state.

### Failure, lifecycle and handoff contract

- Catalog creation is the fail-fast boundary for duplicate methods, invalid declaration shapes and unrepresentable discovery schemas. It must precede listener readiness.
- Decode/Invalid request failures never enter D2. Invalid params, denial and handler failure always use D2 outcomes and close their ALS scope.
- One batch member's promise rejection is captured as that member's error; `Promise.allSettled`-class behavior is required so no batch member can reject the entire dispatch.
- A request abort cancels only cooperative work for that member. Disconnect/transport loss does not become app-owned task cancellation.
- A batch dispatch must not throw after parse/member classification except for a catalog/programmer invariant; wire- and invocation-originated failures are always per-member responses.
- Local CLI mirror failures and network HTTP statuses are adapter concerns. The codec returns protocol data (or no response for a notification), not a `Response`, process exit, argv, MCP tool result or log line. The shared invocation primitive is callable by the local mirror without pretending the CLI supplied a JSON-RPC envelope.
- Listener, CLI, OpenRPC endpoint and relay integration must consume the same catalog instance created by the factory. They must not call separate builders or rederive methods.
