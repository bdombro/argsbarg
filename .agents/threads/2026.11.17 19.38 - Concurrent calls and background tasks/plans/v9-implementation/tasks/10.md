## Brief

### Why

The config helper leaf is implemented and accepted, but consumers cannot reach `resolveConfigDir` through the package's sole supported import surface yet. The public handoff must expose exactly the accepted helper, explain how apps call it without implying argsbarg owns settings, and turn the existing Unreleased planning note into an accurate shipped-feature note.

### Observed state

- **Implemented leaf:** `src/core/config-dir.ts` exports package-private `selectConfigDir(...)` plus `resolveConfigDir(appKey, override?)`. The latter samples process platform/environment/home, resolves a normalized directory and performs one recursive `mkdir` only when called. Its exact D3 validation and failure behavior is accepted; task 7's final targeted run passed 9/9 tests.
- **Package boundary:** `package.json` exports only `"."` (`dist/index.js` plus declarations), and `src/index.ts` is the explicit source barrel. `selectConfigDir` must remain reachable only to repository code through the leaf module, not from `"argsbarg"`.
- **Docs:** `docs/cli-program.md#app-settings` is the authoritative authoring guide. It currently calls the helper “planned,” and links to `docs/use-cases/settings.md#resolve-settings-across-installs`, which currently documents the same plan and platform defaults. These are the two config/settings documentation owners. `README.md` only points to the guide and needs no change.
- **Changelog:** `[Unreleased]` has the Keep a Changelog-style bullet vocabulary (`New`, `Fix`, `Docs`, `Planning`) and an existing planning bullet about the opt-in config-directory helper.

### Target and non-goals

After this handoff, consumers import only `resolveConfigDir` from `"argsbarg"`; its signature and runtime behavior remain unchanged. The authoritative docs state the accepted signature, call-time creation, platform locations, override rule, strict/fail-closed path policy, and app ownership of settings/storage. `[Unreleased]` records the new public helper without changing the package version.

No package subpath, selector export, factory/server wiring, startup hook, config loader, environment discovery, settings schema, storage abstraction, dependency, template/example change, migration guide, or `8.x` compatibility promise is part of this task. Do not touch the accepted implementation, tests, `package.json`, lockfiles or dist.
