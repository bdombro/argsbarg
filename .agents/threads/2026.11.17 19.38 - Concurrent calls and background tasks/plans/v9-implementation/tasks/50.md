## Brief

Brief identity: task 50 contract rev 1 + accepted DP-23 task 33/implementation tasks 41/43/44 + accepted DP-24 task 34

Split MCP 2026 I/O into two package-internal adapters over the one accepted `McpRegistry` and `dispatchMcpRequest`. The stdio adapter owns newline framing, the raw stdout protocol writer and request controls; the HTTP adapter owns `/mcp` Request/Response framing, `Mcp-Method`/`Mcp-Name`, mount-local admission/OAuth handoff and disconnect behavior. Neither adapter recreates discovery, protocol validation or dispatch. The integration owner constructs one registry per process and injects that same object into the selected adapter and later mirror/relay command wiring. A remote relay never substitutes a remote catalog for that fixed local registry.

Status: ✅ refined

Independent refinement: completed by task 54. The stdio slice is ready after acceptance of this refinement. The HTTP slice additionally waits for the accepted DP-24 listener implementation/review handoff; Tasks and OAuth remain sibling owners.

### Why and canonical context

- DP-23 supplies one immutable caller-independent `McpRegistry`, the pure `2026-07-28` `decodeMcpRequest`/encoder and one `dispatchMcpRequest`. D2 supplies `InvocationBase`, exclusive `local`/`http` source views, fresh typed locals, cooperative `AbortSignal`, output capture and `InvocationOutcome`.
- Current `src/mcp/server.ts` proves useful 8.x constraints—raw stdout bypass, concurrent calls, per-ID cancellation, progress-token validation, atomic output and recoverable framing errors—but combines them with legacy `initialize`, roots, argv conversion and session negotiation. It is prior art only; v9 must not preserve or route through those behaviors.
- The settled architecture permits one selected MCP transport per process. Stdio opens no listener; HTTP mounts only `/mcp` on DP-24's shared listener and may coexist with REST/RPC mounts. Requesting both MCP launch modes is a startup error before either transport binds or starts.
- Stdio and local mirrors see only launch-owned process environment. HTTP calls see only request headers and mount-verified caller locals. No implicit env-to-header copy, fallback, cross-source view or credential forwarding is allowed.

### Current and target state

Current:

- `src/mcp/registry.ts` fixes exact tool names, immutable schemas/annotations, deterministic ordering and a typed native invocation closure.
- `src/mcp/protocol.ts` accepts only `2026-07-28`, validates JSON-RPC IDs/envelopes and request `_meta`, rejects `initialize`, and stamps `resultType`, cache fields and server identity.
- `src/mcp/dispatcher.ts` serves `server/discover`, `tools/list` and `tools/call`; invokes each valid call exactly once through `invokeBound`; and returns a protocol response or `undefined` for notifications.
- The legacy stdio loop performs incremental NDJSON reading, suppresses cancelled results, emits progress to raw stdout and installs output isolation. It still derives tools from CLI argv, negotiates old revisions, changes cwd through roots and serializes calls by default.
- No v9 MCP HTTP mount, local `mcp call` native mirror or relay client exists.

Target:

- A stdio process and an HTTP process built from the same declarations each construct one registry instance at startup. The selected adapter, discovery and invocation consume that exact object without rebuilding tools per request. Separate processes share no framing, active-request or cancellation state.
- Each request gets a fresh base `{ surface: "mcp", source, signal, locals }` plus exactly one source view. Discovery/list can reuse the registry without a handler source; a call base is created only after protocol/header/middleware admission.
- Calls overlap by default. A blocked call cannot prevent a later call from progressing. String and numeric IDs remain distinct. Stdio rejects a duplicate active ID without invoking; concurrent HTTP POSTs remain isolated and may reuse the same request ID.
- Stdio cancellation aborts only that request's signal and suppresses its later protocol result. It does not cancel sibling calls, durable task work or the connection; finished/unknown cancellation IDs are no-ops. HTTP cancellation in this slice is the exact request/response disconnect signal.
- Progress uses the validated request `_meta.progressToken`; the reporter is request-local, no-ops after terminal/cancellation and rejects non-finite, non-increasing, negative or over-total updates. The protocol's concrete reporter belongs in typed MCP seed locals, not a new global or handler context wrapper.
- Stdio writes JSON only to raw stdout. App stdout outside an invocation is redirected to stderr for the adapter lifetime; handler stdout/stderr remains captured and absent from protocol messages. Restore the prior outside-write policy on exit.
- HTTP denial, auth failure and validation settle before an SSE response starts. Disconnect aborts only the request/stream; transport loss is never task cancellation.

### Stdio adapter contract

Create `src/mcp/stdio.ts` as a package-internal NDJSON adapter. It accepts the registry, server identity/instructions, a typed factory for local seed locals and an injected lifecycle/log sink; it imports no listener, `Request`, HTTP middleware or factory launcher.

Behavior:

1. On entry, install invocation-scope output protection, capture `rawStdoutWrite`, and redirect unscoped stdout to stderr for the adapter lifetime. The frame writer serializes complete bytes and honors writer `drain`/failure only; it never serializes decode, admission or handler execution. A write failure rejects the loop instead of allowing later frames past it.
2. Incrementally decode stdin bytes with one `TextDecoder`. Empty whitespace lines are ignored. A final unterminated non-empty frame is processed at EOF. Feed each complete text/value frame to `decodeMcpRequest`; write its exact protocol error for malformed JSON/envelopes and continue.
3. For a valid request with an `id`, register an active `AbortController` before asynchronous dispatch. Duplicate active IDs produce `-32600` with the original ID and do not call the dispatcher. Notifications have no response and do not enter the active-call map; a notification other than cancellation is still offered to the dispatcher and its `undefined` result is not written. Valid request IDs arrive as a string or safe integer from the protocol decoder.
4. Cancellation notifications (`notifications/cancelled`, with `requestId` and optional string `reason`) are intercepted before dispatcher invocation and abort only the matching typed controller. Validate `requestId` and `reason` in the adapter; malformed cancellation notifications are ignored with no response because they are notifications. Unknown, completed or type-distinct IDs are no-ops. The dispatcher sees only the resulting call signal.
5. Build the fresh call-local base with `source: "local"`, `surface: "mcp"`, a read-only process-env `NameView`, the supplied fresh typed seed locals and a progress reporter in those locals. The exact operation can add typed caller data only through the normal guard plan; local paths never synthesize HTTP headers or call HTTP middleware.
6. Dispatch every non-notification concurrently, regardless of arrival order. `process.chdir` stays forbidden by the registry's accepted `invokeBound` closure. Captured stdout/stderr never becomes protocol content.
7. `reportProgress` emits a `notifications/progress` envelope through the raw frame writer with the original token. It is active only while the request is active; reject non-finite, negative, non-increasing or over-total values before emitting. It has no output without a token and no-ops after terminal or cancellation. Suppress the terminal response after abort. A writer/EPIPE failure aborts all active calls and rejects the loop; never write a secondary stdout diagnostic.
8. On stdin EOF, stop accepting frames, await all current requests, remove stdout/error listeners and resolve normally. EOF is transport shutdown, not cancellation by itself. Explicit signal/loop failure follows the lifecycle caller; this adapter does not call `process.exit`, bind sockets, change cwd or request `roots/list`.
9. `initialize`, `notifications/initialized`, `ping`, roots/resources and old revision negotiation are not implemented. A client compatibility probe receives the accepted dispatcher/protocol `initialize` error; no fallback initialization path is added.

### Streamable HTTP adapter contract

Create `src/mcp/http.ts` as a package-internal `/mcp` `HttpMount` factory. It accepts the same registry, server identity/instructions and an app-supplied mount-local admission/middleware function. It owns native `Request`/`Response` framing only; it does not import the Node listener.

Admission and request base:

1. Claim the exact normalized `/mcp` path. Other paths remain unowned and fall through to the listener/other mounts; methods at `/mcp` are owned by this adapter.
2. Require `POST`. Inspect case-insensitive `Mcp-Method` and `Mcp-Name` before consuming the body. `Mcp-Method` is required and must equal the decoded body method. In this tools-only slice, `Mcp-Name` is required exactly for `tools/call` and must equal `params.name`; `server/discover` and `tools/list` require no name and reject a conflicting name. Missing, malformed or body-inconsistent values are native HTTP request errors, never permission for body-only routing. `Mcp-Name` handling for future task IDs belongs to Tasks.
3. Run only `/mcp`'s mount-local admission callback. It may inspect the native immutable request and already parsed method/name/header view, then return an HTTP `Response` (deny/challenge) or fresh seed locals. OAuth metadata, token verification, refresh and challenge construction belong to the OAuth sibling: consume its result, never import, perform or simulate OAuth here. The callback is not a replacement for tool guards and does not apply to stdio, local mirrors or sibling mounts.
4. Pass `source: "http"`, a case-insensitive name-only `headers` view, the listener-provided exact `AbortSignal`, fresh admission/caller locals and `surface: "mcp"` to `dispatchMcpRequest`. Guards/handlers never receive an enumerable `Request` or raw credentials, and the adapter never reads process env or forwards the bearer token. Header-name lookup is case-insensitive; exact values enter locals only when admission explicitly authorizes them.
5. Build a fresh request controller linked to `context.signal`; abort it when the client disconnects or a response stream closes early. Do not treat listener drain as job cancellation beyond its transport request.

Framing and response:

1. Reject unsupported `/mcp` methods with `405`, `Allow: POST`, and no dispatch. This tools slice does not invent a retained GET subscription, DELETE session or server-initiated stream. Future Tasks/subscriptions must decide and extend this policy explicitly.
2. Read and decode one JSON-RPC envelope after header inspection/admission. Batch arrays remain `-32600` per DP-23. A JSON-RPC error response is `200 application/json`; malformed JSON, header/framing mismatches and other native request failures are `4xx`; mount admission returns its own native HTTP response; unexpected adapter/listener failures are sanitized `5xx`. Do not reinterpret a protocol error as an HTTP failure.
3. A call without progress uses `200 application/json`. An admitted notification whose dispatcher result is `undefined` uses `202` with an empty body. Before returning a call response, race only the adapter-owned first-progress event with terminal dispatch completion. If dispatch settles first, return ordinary JSON. If progress arrives first, guards have admitted the call, so return `200 text/event-stream`, emit queued/subsequent progress notifications and the one terminal JSON-RPC result, then close. A denial/error before first progress remains ordinary `200` protocol data; an admission denial remains its native HTTP response. Never upgrade after response headers commit.
4. Each SSE `data:` payload is exactly one MCP JSON-RPC message. Stream through the DP-24 Web body bridge so listener backpressure and reader cancellation apply; never buffer stdout, the whole handler stream or credentials. Progress is not retained after terminal completion and there is one terminal response in this non-Tasks slice.
5. Keep accepted tool guard denials in their MCP-native `structuredContent` result. The accepted dispatcher exposes no transport observation seam for `Denial.http`; this adapter must not scrape protocol result internals or reinterpret `http` data as a status. Scope/challenge HTTP denials that can happen before dispatch belong to the mount-local OAuth/admission sibling. Unexpected thrown values are absent from HTTP text, headers and logs.
6. Use a request-local response/progress queue; do not add a process-global session, tool, progress or result store. For this stateless slice, HTTP request-ID reuse across separate concurrent POSTs is isolated. Transport disconnect aborts that POST's exact listener-provided signal; protocol `notifications/cancelled` across POSTs is not claimed because no cross-request session identity is settled. Test the supported disconnect-cancellation boundary and preserve the unsolved host/session cancellation gap explicitly.
7. `Mcp-Method`/`Mcp-Name`, status, 202, SSE and disconnect behavior is fixture-tested locally only. It does not prove a real host sends/accepts these values, reconnects to a call, emits cross-POST cancellation or preserves a streamed call through proxies.

### Source, cancellation and progress

- The source union is closed: stdio/local mirror use `source: "local"` plus `env`; HTTP/relay destination dispatch uses `source: "http"` plus `headers`. Adapters never expose both.
- Each adapter constructs one `AbortSignal` per call. Stdio cancellation/write failure and HTTP request disconnect abort that exact signal; D2's cooperative checks run at parse, guard and handler checkpoints. An arbitrary synchronous handler or child that ignores the signal cannot be forcibly stopped.
- Progress is transport-owned but invocation-visible through typed seed locals. It reads `request.meta.progressToken`, emits through the stdio raw frame writer or HTTP request-local SSE stream, and observes the same abort/terminal state. It never writes through captured `console.log`, a global store or the returned handler value. There is no progress wrapper in the dispatcher or universal public MCP context.
- The dispatcher retains one result path. Neither adapter parses/revalidates `rawInputs`, reruns guards, changes `InvocationOutcome` or opens a second registry.

### Local mirror and relay handoffs

These are separate future owner slices, not hidden helper code inside either transport adapter.

- **Local `mcp call`:** a generated command accepts one tool name and native JSON arguments, performs exact lookup in the same process registry and dispatches a `tools/call` protocol object with a fresh local base. It uses the same declaration/guards/schemas and `source: "local"`, opens no listener, runs no HTTP middleware and invents no headers. Handler stdout/stderr follows the local CLI encoder, while a protocol tool result follows MCP encoding for parity.
- **`mcp call --relay`:** after exact local registry-name selection, build one native Streamable HTTP `tools/call` request to the supplied `/mcp` URL and include `Mcp-Method: tools/call` plus `Mcp-Name`. Do not run the local declaration or guards on relay and do not fall back locally. Send only explicit relay display/credential options selected by the future CLI/relay decision; never copy all env values into headers. Any DNS, HTTP, decode, auth or remote tool failure remains a relay failure.
- Relay body/headers/protocol construction may be fixture-tested with an injected `fetch`; no live server, host, external issuer or real network is required. Public relay flags/display and credential selection remain a task 20/future decision; this Brief deliberately does not invent them.
- Local mirror/relay integration must not import a private stdio writer or HTTP mount internals. They consume the registry/dispatcher/protocol primitives and their own native I/O policy.

### Selected transport and lifecycle

- The app factory/serve integration owns selection. `serve mcp --stdio` starts only stdio. An HTTP service declaration registers the MCP mount on the shared listener. A process cannot start both MCP transports, bind a listener for stdio, or silently choose one when both are requested.
- Reject combined selection during launch validation, before stdin state is changed or any listener bind begins. Two processes may use different transports with independently constructed registries.
- Adapters stop their own transport work and return/resolve; they never own the app's borrowed resources or call `process.exit`. DP-24 owns listener drain/force; CLI/factory owns signal registration and app cleanup.
- A future public-integration owner serializes cutover from `src/mcp/server.ts`, `src/headless/tool-call.ts`, old `App.invoke` MCP branches, bundle launch args and examples/templates. This transport brief does not edit those shared paths.
