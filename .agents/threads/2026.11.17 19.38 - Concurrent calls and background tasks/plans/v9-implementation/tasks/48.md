### Why and canonical context

- Rationale: accepted task 37 implements `createHttpCatalog`, native path/query/body binding, one `invokeBound` call, DP-21 encoding and catalog-owned OpenAPI. It does not expose an `HttpMount`, generated `api` mirror or relay client.
- D2 and DP-11 fix exclusive `local`/`http` sources, fresh locals, the exact request signal and transport-neutral invocation outcomes. DP-21 fixes the `/api`-relative catalog, error wire, native `Response` identity and catalog/OpenAPI identity. DP-24 fixes the fixed-claim `HttpMount`, no-fallback dispatch and listener-owned streaming/lifecycle.
- Architecture rev 2 fixes independent `/api`, `/rpc` and `/mcp` mounts. REST discovery is `/api/openapi.json` and `/api/docs`; shared `/health/liveness`, `/health/readiness` and `/status` are root framework endpoints, not REST routes.
- Existing `src/http/server.ts` is 8.x prior art only. It currently combines root framework endpoints, CORS/trace/hooks/access behavior, legacy argv dispatch and Node serving. Preserve the useful behavior at an explicit new mount boundary; do not keep the legacy dispatch path in v9.

### Observed current and target state

Current:

- `src/http/routes.ts:createHttpCatalog` freezes one catalog with compiled D2 declarations and source-disjoint input schemas. `matchHttpCatalogRoute` uses normalized, mount-relative paths.
- `src/http/bind.ts:bindHttpRequest` accepts a native `Request`, defaults the mount to `/api`, builds a header-only HTTP source, uses `request.signal`, and preserves the one-parse boundary.
- `src/http/dispatch.ts:dispatchHttpRequest` is already the in-process `Request -> invokeBound -> Response` seam. `src/http/encode.ts` preserves native `Response` identity; `finishHttpResponse` reuses the body stream while applying framework-owned CORS/trace headers.
- `src/http/openapi.ts:generateHttpCatalogOpenApi` emits external `/api` paths from the same fixed catalog. Existing `apiDocsHtml()` still points at `/openapi.json`, so it cannot be reused unchanged for the v9 mount.
- Current `handleApiRequest` supplies request hooks, CORS, `traceparent`, client IP/access logging and root health/discovery. It also calls the legacy `App.invoke` bridge; that path is not a target consumer.
- DP-24 `HttpMount` accepts only `Request` plus `{ signal }`. The listener owns Web/Node streaming, backpressure, disconnect abort, bind and stop behavior. It has no fallback when a claimed mount returns a response.
- There is no v9 REST `HttpMount`, local `api` binder or relay client.

Target:

- One package-internal mount factory closes over the factory-created REST catalog and app identity. It claims the single prefix `/api`; paths outside that prefix are never handled by this adapter and receive the listener's 404.
- The mount handles user routes through `dispatchHttpRequest`, `/api/openapi.json` through the retained catalog and `/api/docs` through REST-owned HTML. No `/openapi.json`, `/swagger`, `/api-rpc`, `/tools/*` or cross-surface discovery is created.
- Wire hooks, CORS and trace finishing occur around the accepted dispatch result. Native handler status, headers (`set-cookie` included) and stream survive. The listener emits transport access facts; the REST adapter does not own sockets or access-log I/O.
- Root `/health/liveness`, `/health/readiness` and `/status` are assembled as separate shared framework claims by the future factory/listener integration. They must not be added as REST catalog routes or claimed by this mount.
- The local `api METHOD /exact/path?...` path selects the same route from the same catalog and calls the same compiled declaration with `source: "local"`, env-only access and an exact caller-owned signal. It creates no `Request`, header view, CORS/trace/hooks, listener or relay attempt.
- A relay branch makes one real HTTP request to the explicitly resolved endpoint and returns the remote native `Response`/safe transport result. It never invokes the local catalog, reads env credentials, synthesizes an authorization header, retries or falls back locally. Credential flags, response display and the public factory contract stay outside this executor.

### Instructions, conventions and capabilities

- New/changed `src/**` files require a multi-line purpose header, human-readable JSDoc for every symbol/property, alphabetically ordered relative `.ts` imports and no production dependency.
- Reuse `HttpMount`, `createHttpCatalog`, `bindHttpRequest`/accepted binding rules, `dispatchHttpRequest`, `generateHttpCatalogOpenApi`, `finishHttpResponse` and D2 `InvocationBase`. Do not duplicate route matching, schemas, invocation, errors, CORS finishing or Node streaming.
- Tests use `node:test`, in-process `Request`/`Response`, injected env/signal/fetch and synthetic streams. No socket, subprocess, listener, external service or network call belongs to this slice.
- Any need to edit `src/runtime/cli.ts`, `src/core/types.ts`, `src/index.ts`, `src/server/**`, docs, examples, templates or changelog is a handoff to the named factory/public owner. The adapter must remain package-internal.

### Decisions and boundaries

Established:

- `decided: DP-21`: the route path excludes `/api`; path/query/body overlap is rejected; one `invokeBound` parse validates the merged flat input; native `Response` is returned by reference without body reads; `Response` status/headers/stream survive.
- `decided: DP-24`: the mount owns fixed claims and receives one request signal. Listener dispatch has no fallback to another mount. A claimed REST path remains REST-owned even when its method/path is unsupported, so this adapter returns the proper REST response rather than asking a sibling mount.
- CORS remains the accepted wide-open policy. CORS and trace are applied after core encoding and override only framework-owned fields. They must not mutate or clone the body stream.
- HTTP guards read request headers only. Local mirror guards read process env only. Neither source can fall back to the other.
- A relay failure is terminal for that command. Remote 4xx/5xx, malformed response, abort and network failure never select local execution.

Required focused decision handoffs, not executor choices:

- Exact relay credential inputs: any `--header`, token/file/env option or credential provider must be settled in one packet shared by REST/RPC/MCP relay owners. Until then the adapter accepts only an explicit header map from its package-internal caller and never imports ambient auth.
- Relay result/display and exit-code mapping: the future CLI/factory owner decides prose, body/binary/stdout behavior and whether a remote status is surfaced as process success/failure. The REST adapter returns a typed transport result and preserves the remote `Response`; it does not print.
- Public `http` block shape, `api` command registration, relay URL resolution and shared framework health/status assembly remain task 20/36/51 factory decisions. This Brief may prescribe consumption of a single catalog and options object but must not add them to `AppSpec` or `src/index.ts`.

Rejected:

- A second or lazily rebuilt REST catalog for mount, OpenAPI, local mirror or relay.
- Reusing `handleApiRequest`, fake argv, `App.invoke`, legacy headless calls or 8.x command-derived routes for v9.
- Constructing a `Request` for the local mirror, copying env into request headers, invoking HTTP hooks for local calls, or opening a listener.
- Catching a relay failure and invoking `dispatchHttpRequest` locally.
- Moving health/readiness, protocol discovery, CORS/trace/access policy, listener lifecycle or sibling protocol semantics into accepted DP-21 leaf code.

### Error, discovery, health and hook contract

| Entry | Required behavior |
| --- | --- |
| `GET /api/openapi.json` | 200 JSON from the fixed dispatch catalog |
| `GET /api/docs` | 200 HTML whose OpenAPI URL is `/api/openapi.json` |
| `OPTIONS /api/**` | 204 CORS response without invocation |
| Supported REST route | Accepted DP-21 bind/guard/dispatch/encode; handler `Response` stream preserved |
| Unsupported `/api/**` route/method | REST 404/accepted error; no sibling/listener fallback |
| `/health/*`, `/status` | Shared framework sibling, not REST catalog/mount; v9 mount tests assert no REST claim |
| Local `api` call | Same catalog/declaration with env-only source, exact signal and no HTTP middleware/listener |
| Relayed `api` call | One explicit network request; remote response/error only; no local/fallback invocation |

- Wire `onRequest` runs before route/discovery handling. `onResponse` runs once after a response exists; `onError` runs once only on a failure classified by the accepted hook contract. Hook errors become one safe generic 500 and cannot bypass CORS/trace finishing.
- Request correlation/trace is mount-local metadata. Raw headers, body, query values, credentials, env, locals and captured stdout/stderr are never logged or serialized by the adapter.
- `finishHttpResponse` may create a new `Response`, but it must pass the same body stream; it must not `text()`, `arrayBuffer()`, clone or buffer. `HEAD`/no-body restrictions remain listener-owned.
- Root health discovery/readiness remains callable for operational probes. It must not appear in the REST OpenAPI document or require a REST declaration. The factory/listener owner proves the root probes use the current `evaluateReadiness` behavior and do not gate invocation.
