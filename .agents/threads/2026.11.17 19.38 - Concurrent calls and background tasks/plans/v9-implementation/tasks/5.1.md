- Question: from `package.json`, `src/index.ts`, `src/server/overrides.ts`, `src/builtins/builtins.test.ts`, and `src/test/integration/mcp.test.ts`, does repository precedent support the proposed async `resolveConfigDir(appKey, override?)`; what stable invalid-input error pattern fits; and is a module-local selector imported only by colocated tests the smallest reversible seam?

## Notes

- Public API: yes. `package.json:18-22` exposes only the package root, and `src/index.ts` is the explicit public export ledger (`src/index.ts:19-23,121-123`). Publish `resolveConfigDir(appKey, override?)` through `src/index.ts`; do not add a package subpath or expose the selector/default-policy helpers.
- Invalid input: use the repository's exported `InputError` pattern (`src/index.ts:19-23`) and a stable, field-specific message for bad `appKey`/non-absolute override. Because the proposed API is async, tests should use `assert.rejects` with a message match. The existing suite uses message-regex `assert.throws` for validation (`src/test/integration/mcp.test.ts:438-449`) and verifies user-input failures surface their message on MCP (`src/test/integration/mcp.test.ts:779-788`). Do not silently ignore/rebase a bad override or fall through to defaults.
- Internal seam: yes. `src/server/overrides.ts:37-46` demonstrates a private selector while `src/server/overrides.ts:48-74` exports only the module boundary used by callers; tests import a source module directly without making it public through `src/index.ts` (`src/builtins/builtins.test.ts:8,111-128`). An exported selector in the config module, imported only by its colocated tests, is the smallest reversible seam: package exports exclude its subpath, and removing it does not alter the root API.
- Concretely rejected: root-exporting platform selector(s), a new package subpath, config loading/storage, path-value echoing in errors, and fallback after invalid override.
- Instruction evidence: explicitly loaded repository `AGENTS.md`, `README.md`, all `docs/*`, swarm `roles/common.md`, and plan `rules.md`; no thread-memory, network, installs, tests, builds or source edits.
- Cleanup: no files or processes created; only this task file was edited.
