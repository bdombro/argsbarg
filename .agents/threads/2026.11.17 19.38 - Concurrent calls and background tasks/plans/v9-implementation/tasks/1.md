**Evidence-backed findings**

1. **Approve the one shared invocation prerequisite.** Seed §§7.1/7.16 and the current `App.invoke`/`src/headless/tool-call.ts` prove that every non-CLI surface currently depends on CLI parsing, argv reconstruction, global app hooks and captured output. The v9 runner contract must be accepted first. Adapter implementation can then proceed in parallel; each adapter should not wait for the factory implementation.
2. **The shared runner decision must settle semantics, not just function names.** The predecessor `App.invoke` validates after hooks, accepts synthetic `toolArgs`, uses one global handler context, and exposes an outcome coupled to captured stdout and response state. The accepted contract must cover: declaration-generic typed input/output, validation order, source-specific caller and `signal`, guard/default/supplement/replace composition, denial representation, domain error representation, native result/`Response`, cancellation, and per-call `locals`. This remains the critical-path decision in task 2, not a refiner decision.
3. **REST is a two-slice dependency, not one task.** Route declaration, source-separated path/query/body binding, collision rejection, REST discovery and adapter fixtures need only the accepted invocation contract. Network wiring needs the shared listener contract. The 8.x `httpRequestToArgv` path and precedence merge (`body`, `query`, `pathParams`) are evidence the current bridge cannot be adapted in place without violating v9 collisions/source rules.
4. **Listener lifecycle/streaming is independently preparable but must be integrated before REST/JSON-RPC/MCP HTTP.** `toFetchRequest` and `writeFetchResponse` currently buffer full request/response bodies, while `httpServeHttp` never closes or returns. A listener slice must own mount composition, streaming/backpressure/disconnect behavior, bind rollback, shutdown/drain, owned-vs-borrowed sockets, and a normal running handle. Catalog/codec slices can start against it before its implementation is finished.
5. **JSON-RPC is independent of REST after the runner.** It gets its own declarations, method registry, codec, batch semantics and OpenRPC generator. Only HTTP mounting, startup selection and integration wait on the listener contract. No REST-generated route dependency is valid.
6. **MCP separates cleanly at the registry/dispatcher.** MCP-native tool registry/dispatcher and caller-aware guarded invocation come first. Stdio framing and Streamable HTTP adaptation can then be separate slices. Stdio needs no listener. HTTP needs the listener and mount middleware contract. OAuth and task-provider support need only the accepted dispatcher/caller/callback boundaries plus their own focused decisions; neither should block base stdio.
7. **Mirrors and relay wait per surface, not on all servers.** The CLI `api`, `rpc` and `mcp call` mirrors each need that surface's accepted declaration/binder and local credential source. Relay clients need their native wire codec and can be fixture-tested before a live server; each final verification waits only on its matching network adapter. No fallback to local invocation is valid after relay failure.
8. **Children wait on registry plus guard/mount semantics.** Child namespace, scoped source views and typed caller handoff need accepted registry and guard-composition contracts. They do not need listener implementation, OAuth, Tasks, packaging or relay clients. Final standalone-versus-mounted checks require the relevant enabled surfaces.
9. **Config helper is independent.** Platform-default resolution and explicit absolute override behavior can be implemented and accepted against its own API contract. Public-root export and factory/example integration are later handoffs to the single export/factory owner.
10. **Packaging/docs/templates are last for integration, not for drafting.** Public declaration, launch, and executable names are prerequisites for final edits and examples. Independent owner files can be staged earlier, but every published path must be integrated against the one executable after surfaces are verified.

**Dependency revisions for the map**

- Invocation contract -> CLI binding, REST binding, JSON-RPC method binding, MCP registry/dispatcher.
- Shared listener contract -> REST network mount, JSON-RPC `/rpc`, MCP HTTP `/mcp`. REST route/OpenAPI and JSON-RPC method/OpenRPC do **not** wait for listener implementation.
- MCP registry/dispatcher contract -> stdio framing, MCP HTTP adapter, `mcp call` mirror and relay, OAuth integration, Tasks integration. OAuth and Tasks remain independent siblings.
- Each native declaration/binder -> its same-surface local mirror -> same-surface integration verification.
- Registry + guard composition -> child mounts. The config helper remains independent of all of these.
- Public declaration + launch contracts and verified native surfaces -> packaging/templates/public docs/final examples.
