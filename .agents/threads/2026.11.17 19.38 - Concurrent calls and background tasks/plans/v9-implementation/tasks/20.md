### Why and canonical context

- D2 is binding: adapters bind native values; `src/runtime/invoke.ts` owns validation/guards/handler execution; adapters encode outcomes. No fake argv, fake requests or runner-owned wire writes are allowed.
- Architecture rev 2 keeps `argsbarg(spec)` and `app.run()`, independent surface declarations, local-only credential views, and normal resolution from `run()` so app cleanup can run.
- Current CLI routing and help are coherent: `parse`/`postParseValidate` select a leaf and retain path params; `cliHelpRender` renders parser paths; `preloadPipableJson` is the stdin bridge. Preserve them.
- Input loading is not binder-ready: `loadLeafInputs` constructs a `CommandContext` and performs Zod validation inside that context. A D2 binder must instead separate parser/coercion from validation so `invokeBound` is the only place that calls the declaration schema.
- `buildCommandInputSchema` emits JSON Schema only. `BoundDeclaration` requires a Zod schema, so commands without `inputSchema` receive a task-owned runtime Zod schema rather than reuse of the JSON-Schema emitter.
- The accepted invocation core is complete in `src/core/invocation.ts` and `src/runtime/invoke.ts`. Consume `BoundDeclaration`, `compileGuardPlan`, `InvocationBase` and `invokeBound` as implemented; do not redefine their contracts.
- App hooks remain a separate current public lifecycle from D2 guards. `src/runtime/cli.ts` owns their accepted
  wrapper around `invokeBound`; no binder or guard compiler hides `beforeInvoke`, `afterInvoke`, `formatError` or
  `onError` inside validation.

### Observed current and target state

Current:

- `argsbarg()` returns `App` in `src/runtime/cli.ts`. `App` validates/freeze-holds the spec and caches parse/presentation roots.
- `prepareDispatch()` parses argv and resolves the runnable leaf. `run()` then preloads piped JSON, constructs `CommandContext`, runs app hooks, validates lazily through `ctx.inputs`, calls the handler and calls `process.exit()`.
- `invoke()` repeats most of that flow inside `runInInvocationScope`, returning the legacy `InvokeResult`. HTTP and MCP currently call it through `src/headless/tool-call.ts`, which converts their values to argv.
- `CommandContext` owns old CLI conveniences and transport data: `args`, `opts`, `inputs`, `pathParams`, `respond()`, `toolArgs`, `runtime` and MCP progress/cancellation. The accepted `BoundDeclaration` handler instead receives validated `InvocationContext` data.
- The public `command()` typing returns `CommandContext`, so no current CLI declaration is directly assignable to `BoundDeclaration.handler`.
- Source tests and examples rely on `CommandContext` convenience members. A `src/core/types.ts`-only cutover will therefore not typecheck the current repository unless the accepted packet includes an explicit compatibility layer or assigns consumer migrations.
- Help and parser use the same command tree, while the core runner uses a compiled declaration. Registration therefore has to preserve the one selected leaf and command path in both views.

Target:

- Factory construction registers each CLI-capable runnable leaf once in an internal catalog. Built-ins remain on the existing built-in dispatch path.
- `src/cli/bind.ts` owns argv-to-native binding after parse: options, positionals, path params, piped JSON, document input, coercion and the local `NameView`/`InvocationBase`. It never validates with Zod, and it never calls a handler.
- `src/runtime/cli.ts` owns `argsbarg`/`App`, catalog registration, startup lookup and the CLI call orchestration. It calls `invokeBound`; it does not parse request bodies or infer REST/RPC/MCP declarations.
- `src/cli/encode.ts` owns CLI-native rendering of `InvocationOutcome`: return/output, denial, invalid input, `AppError`, unknown throws and exit status. Parser, preload, help and built-in failures settle before `invokeBound` and use the same CLI terminal policy.
- `app.run()` sets `process.exitCode`, flushes stdio and resolves normally on user-command completion. It does not call `process.exit()` on the new user-command path. Existing service/bundle built-ins and their shutdown are separate launcher work.
- `App.invoke(argv)` is the non-exiting CLI entry and defaults to `surface: "cli"`. During the unreleased native-adapter cutover only, its explicit `invocation: "http" | "mcp"` option selects a marked legacy branch with `toolArgs`, request data and `InvokeResult`. - REST task 21: receives a separate native route catalog and may register it through the future factory integration seam. It owns `src/http/bind.ts`/`src/http/encode.ts`, path/query/body collisions and `Response` streaming.

- MCP task 23: receives the MCP declaration registry/dispatcher and local/stdin/HTTP source construction; task 20 supplies no MCP framing, tool catalog or mirror implementation.
- Local mirrors: `api`, `rpc` and `mcp call` use each owning adapter's registered `BoundDeclaration` with `source: "local"` and the adapter's real `Surface`; they must not synthesize HTTP headers or invoke an HTTP/MCP transport. ### Failure, cleanup and lifecycle

- Any parse/bind or registration error settles before `invokeBound`. Bind failure cannot call a guard, handler or
  `beforeInvoke`; it may use `formatError`/`onError` after a base exists.
- Invalid input and denials close the invocation scope and encode zero handler effects.
- `App.run()` must set `process.exitCode` and resolve normally on migrated user-command paths. It must flush stdout/stderr before resolving so large piped output is not truncated. Service/bundle built-in lifecycle remains outside this migration.
- The task does not own signal handling or listener drain. `App.run()` must not close borrowed app dependencies.
- A handler/guard that schedules late async output after settlement follows existing `invocation-scope` closed behavior; the encoder never reopens that scope.
- Cancellation supplied to local calls must be checked by `invokeBound`. A never-aborted controller is valid for plain CLI calls; synchronous code cannot be forcibly interrupted.
- Do not log raw env/header values, raw inputs, locals, `NameView` objects or denial challenges.

### Errors and compatibility contract

- Parser/coercion errors keep current wording/help context. The binder must not recast parser errors as Zod failures.
- Invalid CLI values are `InvocationOutcome.kind === "invalid"` with the original `z.ZodError`; the encoder formats them, it does not rethrow them.
- Denials are distinct from invalid input and handler errors. Default `false` is `DENIED / Access denied`; structured denials retain their stable code/message.
- `AppError` remains a normal thrown value in `kind: "error"`; CLI uses `code`, `message` and a safe nonzero code but never HTTP-only `httpStatus` or `challenge`.
- Unknown thrown values must not be string-flattened into raw data. Keep the full `Error.message`; use a generic message for non-`Error` values.
- Successful return values continue to serialize as CLI output after captured output. No protocol result envelope is introduced.
- `App.invoke(argv)` defaults to native CLI. The exact old `InvokeResult`, response and HTTP/MCP options survive
  only on the marked explicit legacy branch; no public A handler receives `CommandContext`, and the integration
  owner removes the branch after tasks 21/23.
