### Observed current and target state

**Current.**

- `src/json-rpc/catalog.ts` creates one immutable fixed catalog and rejects duplicate/unrepresentable methods before any call.
- `src/json-rpc/dispatch.ts` accepts text/value input, executes independent batch members through `invokeBound`, links one member signal to its parent, suppresses valid notifications and returns protocol data rather than a `Response`.
- `invokeJsonRpcMethod` is the direct primitive for a local mirror: it accepts a catalog, exact method, raw params and one `InvocationBase`, and never fabricates an envelope.
- `src/json-rpc/openrpc.ts` generates OpenRPC 1.3.2 from the same catalog and app identity.
- `src/core/invocation.ts` fixes the two source variants: local calls expose only `env.get`; HTTP calls expose only case-insensitive `headers.get`. Neither source falls back to the other.
- DP-24 supplies `HttpMount` claims and one request `AbortSignal`; current listener source implements that package-internal boundary, but task 46/47 review and acceptance remain the listener prerequisite. There is no JSON-RPC `HttpMount`, local `rpc` built-in or relay client today.
- The factory still knows only the 8.x CLI/HTTP/MCP spec. `src/runtime/cli.ts` is the serialized factory/serve owner; `src/index.ts` is the serialized public integration owner.

**Target.**

- One package-internal HTTP adapter claims exact paths `/rpc` and `/rpc/openrpc.json`, consumes the fixed catalog supplied by the factory and never builds a second catalog.
- `POST /rpc` passes the complete request body to DP-22 dispatch, creates a fresh HTTP `InvocationBase` for every batch member, and returns:
  - `200` plus the JSON-RPC success/error value for any request-bearing single call or batch;
  - `204` with no body for a valid single notification or an all-notification batch;
  - protocol errors inside a `200` JSON-RPC envelope, not REST/HTTP exception bodies.
- `GET /rpc/openrpc.json` returns the catalog's OpenRPC document as JSON. No MCP or REST schema is consulted.
- A local `rpc` adapter parses one native params value, uses the direct method primitive with `source: "local"`, process-env access and no HTTP request, listener or synthetic header view.
- `--relay <url>` is parsed by the factory owner and sends a real JSON-RPC `POST` to that exact endpoint. It does not call a local handler, start a listener, copy env into headers or fall back after a remote/network/protocol failure.
- Mount and local paths consume the one factory-created DP-22 catalog. Relay consumes the same registered method names at the factory boundary but never opens the local catalog for dispatch or discovery. No path generates methods from REST or MCP.

### Decisions and alternatives

**Established.**

- `decided: DP-22`: strict JSON-RPC 2.0; finite string/number/null IDs; exact method names; direct object/array/omitted params; independent non-atomic batches; valid notifications execute but emit no envelope; OpenRPC 1.3.2; request-bearing HTTP status is `200`, notification-only status is `204`.
- `decided: DP-24`: one package-internal `HttpMount` has flat exact/prefix claims and `handle(request, context)`; the only mount context is the exact request `AbortSignal`; Node bridging, bind, shutdown and streaming remain listener-owned.
- D2/DP-11: adapters create only native raw inputs plus `InvocationBase`; `invokeBound` performs the sole schema parse and guards/handler run. Captured output, locals, caller and cancellation are per call.
- Architecture/seed: HTTP request credentials come only from request headers; local/CLI calls come only from process env. No listener, synthetic `Request`, synthetic argv or protocol fallback is valid for the local mirror.

**Selected within this Brief.**

- Model the HTTP adapter as one pure mount factory that closes over the factory-created catalog and app identity. Give it exact claims for `/rpc` and `/rpc/openrpc.json`; never infer a mount path from program or route config.
- Return transport-native `Response` values. The adapter may read this JSON body into text, because JSON-RPC is not a streaming-upload protocol; the listener still owns incremental Web/Node bridging.
- Keep local and relay execution in one `mirror.ts` module because both serve the generated `rpc` command, but expose separate functions and never allow the relay branch to call local dispatch.
- Keep relay I/O behind an injectable fetch-compatible function for deterministic unit tests. The production factory supplies global `fetch` by default.

**Factory-owned relay and display boundary.**

- `invokeJsonRpcLocal` returns the accepted transport-neutral `JsonRpcMethodOutcome`. A valid relay `result`/`error` envelope must map to that same outcome; the accepted DP-22 error object and code-to-category mapping are fixed.
- The relay transport-error shape, exported function/options signature, generated ID policy and any explicit credential/header mechanism are shared with the future CLI/factory owner. They are not settled by this transport Brief. Task 36/51 must own one focused decision before task 49 executor dispatch; that decision must also pin CLI display/exit mapping if multiple owners consume the shape. Do not make the adapter depend on `process.stdout`, `process.stderr`, `process.exit`, legacy `CommandContext`, global auth state or guessed `--header`/`--auth` flags.
- Until that decision accepts explicit credential forwarding, relay sends only the required JSON content type and caller-controlled abort, URL and injected fetch dependencies. It never reads a credential env name, copies request/app state, acquires credentials, retries or falls back. Omitting a credential option does not authorize implicit forwarding.

**Rejected.**

- Calling `dispatchJsonRpc` with a fabricated envelope for local calls: it would create a false wire origin and notification/ID behavior.
- A relay branch that first invokes locally or retries locally on fetch/timeout/error: explicitly violates no fallback.
- An adapter-owned global catalog or lazy registration: discovery and dispatch would drift and duplicate factory work.
- Reusing MCP's JSON-RPC server/parser or REST's `App.invoke`: MCP framing and REST argv binding have different semantics.
- Mapping JSON-RPC application/protocol failures to 4xx/5xx: the request reached the JSON-RPC endpoint and retains a `200` response envelope; only notification-only success uses `204`.
- Logging request bodies, headers, env, locals, params or raw thrown values for diagnosis.

**Assumptions.**

- The listener keeps the complete request URL and supplies the same abort signal in `HttpMountContext`, as DP-24 accepts.
- The accepted executor-facing factory owner will make a catalog once and provide stable app title/version/description. If task 51 changes that owner or interface, only the factory handoff section of this Brief reopens.
- CLI stdin JSON parsing and output presentation are not owned here; the adapter API must support a future `rpc` command without deciding framework-global CLI behavior.

### Behavior and error contract

| Entry | Required behavior |
| --- | --- |
| `POST /rpc` request-bearing call | `200`, one JSON-RPC response envelope |
| `POST /rpc` mixed batch | `200`, only response-bearing members in completion order; no atomic rollback |
| `POST /rpc` valid notification/all-notification batch | `204`, no body, no rewritten sibling |
| Parse/envelope/method/params/guard/app/internal RPC failure | `200` with accepted DP-22 JSON-RPC error; never a REST envelope |
| `GET /rpc/openrpc.json` | `200 application/json`, same fixed catalog as dispatch |
| Wrong method at claimed RPC path | `405` plus `allow`; generic JSON body |
| Local `rpc` call | Direct method invocation; local env only; native outcome; no envelope, listener or HTTP middleware |
| Relayed `rpc` call | Exact endpoint, one JSON-RPC request, remote result/error only; no local invocation or env-header fallback |

- HTTP `204` is selected from `dispatchJsonRpc` returning `undefined`, not by inspecting method names, counts or handler values.
- A JSON-RPC denial remains a protocol response with the DP-22 `-32001` body, even if its `Denial.http` field proposes another HTTP status. Likewise, `AppError.httpStatus` must not change the HTTP status here.
- The notification observer is bounded and must not be allowed to replace the response. If observation rejects, DP-22 dispatch still settles that notification without a wire response; a mixed sibling remains unchanged.
- Each HTTP batch member receives its own fresh locals and linked signal. Calls from separate requests never share locals, output scopes or header objects.
- Relay is single-request in this CLI slice. Server-side batch support remains tested through the HTTP adapter; do not invent a relay batch syntax.
- JSON serialization belongs to DP-22's strict safe result/error values. The adapter must not perform a second permissive `JSON.stringify` policy or append captured stdout/stderr.

### Failure, cleanup and lifecycle

- Mount construction fails fast when its required catalog/app identity contract is invalid; it performs no I/O and opens no resource.
- HTTP body-read failure or mount exception before protocol dispatch returns generic transport failure and cannot leak the raw body/error. Once the listener has begun writing a response, its DP-24 bridge owns stream termination.
- Request disconnect aborts only the request/member signal. It does not stop the listener, cancel another batch member from a different request or cancel app-owned durable work.
- Local parsing failure never calls catalog lookup, guards or a handler. Relay construction failure never calls local dispatch. Relay abort/network failure cannot initiate a second fetch, OpenRPC request or local fallback.
- No adapter owns process signal handlers, borrowed resources, long-lived timers, cleanup handles or sockets.
- A mount observer may be asynchronous but cannot outlive the request's terminal wire decision as an untracked side effect. Notification observation is already awaited by DP-22 dispatch; application code remains responsible for any durable observation store.
