## 1. Approve the phase 1 contract

Status: ✅

Approved with one condition: no breaking changes, released as a patch. Concurrency becomes the default later, in httpbarg/toolbarg

### Overlapping calls are isolated

`app.invoke` and the HTTP server already run calls side by side (node:http doesn't queue), and overlapping calls currently mix their captured output. Per-call capture fixes that with no API change:

```typescript
await Promise.all([
  app.invoke(["wait", "--after", "42"]),
  app.invoke(["send", "--message", "approved"]),
]); // each result gets only its own stdout/stderr
```

### Opt-in MCP concurrency

```typescript
mcpServer: {
  enabled: true,
  concurrent: true, // default false: calls stay serialized as today
},
```

Gateway: `argsbarg gateway --concurrent a.mjs b.mjs`; refuses to start if a bundle predates the invocation-scope contract ("rebuild with argsbarg ≥ X")

Async overlap only; synchronous JavaScript still blocks the event loop. No framework serial option: apps that opt in and share state use their own lock or transaction

### chdir in concurrent MCP mode

```typescript
handler: async (ctx) => {
  process.chdir("/repo/a"); // throws in concurrent MCP mode: "process.chdir isn't allowed inside a command; pass the directory as an argument"
  await execFileAsync("git", ["status"], { cwd: ctx.inputs.dir });
},
```

Only inside invocations of an MCP server with `concurrent: true`; everything else is unchanged. Roots workspace selection still runs once before the first call

## 11. Build the task core

Status: 🛑

Depends on item 10. Agreed design:

Per-command opt-in, no global switch: tasks are on when any tool sets `execution.tasks`. The MCP tasks extension is opt-in on both sides and server-directed, with no per-tool flag

```typescript
// Optional root settings, all with defaults
tasks: {
  maxTasks: 1000,
  pollInterval: "1s",
  store: { path: "~/.local/state/myapp/tasks.sqlite" }, // default; "memory" for tests
  ttl: "1h",
},

// A slow tool opts in; promoteAfter sets the behavior
execution: {
  tasks: {
    maxActive: 2,        // more concurrent runs get a capacity error
    promoteAfter: "5s",  // run inline; become a task after 5s. 0 = return a task immediately
    timeout: "10m",      // abort the signal and fail the task after this, counted from start
    ttl: "15m",          // keep this tool's results shorter than the root ttl
  },
},
handler: async (ctx) => {
  ctx.reportProgress(0, 1, "Starting");
  await rebuildIndex({ signal: ctx.signal });
  ctx.reportProgress(1, 1, "Finished");
  return { indexed: true };
},
```

```typescript
const task = await app.tasks.start("rebuild_index", args);
const state = await app.tasks.get(task.taskId);          // status, progress, inputRequests, result | error
await app.tasks.update(task.taskId, { inputResponses }); // answer pending input
await app.tasks.cancel(task.taskId);
const done = await app.tasks.wait(task.taskId);          // resolves at a terminal status
const mine = await app.tasks.list({ owner: "local" });
```

- `promoteAfter` is required whenever `execution.tasks` is set; `timeout` and `maxActive` apply inline or as a task
- Store: `node:sqlite` in WAL mode; engines `>=22.13`, where it works without a flag (stderr ExperimentalWarning is acceptable)
- Shared store with per-task leases: the running process heartbeats; another process marks a task failed only after its lease lapses. Cross-process update and cancel go through the store
- Recovery: terminal results survive restarts; interrupted work (including work waiting for input) becomes `failed`; nothing reruns
- Durably create the task before returning its handle; storage errors fail the request
- Owner on every record (stdio: local OS user, so a new session can poll tasks from an earlier one); IDs from `crypto.randomUUID`
- TTL from creation, `maxTasks` and `maxActive` caps with explicit capacity errors, `timeout` aborts and fails, expiry cleanup, binary results stored losslessly
- Timed promotion is toolbarg's design: the extension lets the server decide per request and doesn't say when
- Shutdown (stdin closes or SIGTERM) aborts active tasks and records them failed immediately; no grace period
- Store location: `$XDG_STATE_HOME/<key>/tasks.sqlite` (fallback `~/.local/state/<key>/`), `%LOCALAPPDATA%\<key>\` on Windows; dir 0700, file 0600; gateway apps each keep their own
- Store creation: at server startup (and on first `app.tasks` use) only when at least one tool sets `execution.tasks`; startup also runs lease recovery
- Status flow working ↔ input_required → completed | failed | cancelled; terminal is immutable; `isError` results mean failed
- Write enabling tasks into toolbarg's decisions doc: it writes a file outside `dist/`

## 12. Add MCP tasks and interactive input

Status: 🛑

Depends on item 11

```typescript
handler: async (ctx) => {
  const { confirm } = await ctx.requestInput({
    message: "Deploy to prod?",
    schema: z.strictObject({ confirm: z.boolean().describe("Approve the deploy.") }),
  });
  if (!confirm) return { deployed: false };
  return deploy();
},
```

| Client | Behavior |
| --- | --- |
| Declares tasks | Promote to task, `input_required`, answer via `tasks/update`; handler stays suspended |
| Elicitation only | Multi-round-trip `InputRequiredResult`; the retry reruns the handler and `requestInput` returns the answer |
| Neither | Error naming the missing capability |

- `io.modelcontextprotocol/tasks` in `server/discover`; never return a task to a client that didn't declare the extension; `tasks/get` returns result or error at terminal; `tasks/update` and `tasks/cancel` return an empty ack
- Schemas must be flat objects of primitives (elicitation limit); rejected when `requestInput` is called. Decline/cancel throws `InputDeclinedError`
- The retry path reruns code before `requestInput`, so document asking before side effects
- `requestState`: HMAC with a per-store secret, binding owner, tool, argument digest, and short expiry; reject tampered or mismatched state
- Duplicate or stale `tasks/update` answers ignored; cancel or expiry while waiting rejects `requestInput`
- Sampling and roots input requests aren't sent (deprecated in 2026-07-28)

## 15. Add HTTP tasks and interactive input

Status: 🛑

Depends on item 14. Copy toolbarg's task core and input handling into httpbarg

```bash
curl -X POST localhost:3000/rebuild-index -H 'Prefer: respond-async'          # 202 + Location: /tasks/{id}
curl -X POST localhost:3000/rebuild-index -H 'Prefer: respond-async, wait=5'  # result if done in 5s, else 202
curl localhost:3000/tasks -H 'Authorization: Bearer abc'                      # caller's tasks only
curl localhost:3000/tasks/{id}                                                # state; result when terminal
curl -X POST localhost:3000/tasks/{id}/input -d '{"inputResponses":{...}}'
curl -X POST localhost:3000/tasks/{id}/cancel
```

- RFC 7240 `Prefer: respond-async[, wait=N]` on existing routes; `wait=N` overrides `promoteAfter`; `Preference-Applied`; 202 + `Location`
- `/tasks` list/get/input/cancel routes, reserved only when a route opts into tasks; startup rejects conflicts; OpenAPI lists them
- Ownership: `Authorization: Bearer <token>` → sha256 owner, raw token never stored; `tasks.owner(ctx)` hook returns a verified principal instead; no header → anonymous tasks, reachable only by ID and never listed
- `requestInput`: with `Prefer: respond-async`, task `input_required` answered via `POST /tasks/{id}/input`; sync request gets 409 telling the client to retry with `Prefer`
- Shutdown on SIGTERM aborts active tasks and records them failed

## 17. Not doing

Status: 🚫

- Shared code between the three libraries: chosen for clean separation; duplication is the accepted cost
- CLI task management: use httpbarg, toolbarg, or `app.tasks`
- CLI `requestInput`: argsbarg is CLI-only after the split and keeps the flags-first rule; revisit if wanted

- Worker threads: handlers close over state that can't cross threads

- Per-invocation cwd: the MCP spec says to pass directories as arguments instead; chdir inside a command throws
