# 8.x MCP gateway bundles vs next-major child mounts

Disposition: resolved by v9. Runtime gateway loading was removed; build-time keyed child
composition was implemented. Keep this note for the historical 8.x/runtime-gateway comparison.

A focused comparison of how 8.x's `argsbarg gateway` (`mcpGatewayRegistry`) works today, where it collides with next-major design decisions, and the two concrete options for handling multi-bundle MCP hosting in v9.

## What exists in 8.x today

In 8.x, every stdio MCP server spawns a fresh Node process (~30 MB RSS before app code runs). `argsbarg gateway` solves that at **runtime** for already-built single-file plugin bundles (`.mjs`) without compiling a new combined app.

From [`docs/mcp.md`](../../../../docs/mcp.md#mcp-gateway):

> Every agent session starts one process per stdio MCP server, and each Node process costs about 30 MB before any app code runs. `argsbarg gateway` serves several argsbarg plugin bundles from one process instead:
>
> - **Entries** are `[alias=]path`. The alias (default: the app key) prefixes each tool: `notes_read`.
> - **Bundles join unchanged.** The gateway imports each one; its `await app.run()` finds the gateway and registers its MCP handler instead of reading argv or stdio.

How it works under the hood relies on a `globalThis` side-channel between two copies of argsbarg (`src/mcp/gateway.ts` and `src/runtime/cli.ts`):

```typescript
// src/mcp/gateway.ts
export const MCP_GATEWAY_REGISTRY = Symbol.for("argsbarg.mcp.gateway");

export async function loadGatewayApps(entries: McpGatewayEntry[], concurrent = false) {
  const globals = globalThis as Record<symbol, unknown>;
  for (const entry of entries) {
    let registered: McpGatewayApp | undefined;
    globals[MCP_GATEWAY_REGISTRY] = {
      concurrent,
      register(app) { registered = app; },
    };
    try {
      await import(pathToFileURL(resolve(entry.path)).href);
    } finally {
      delete globals[MCP_GATEWAY_REGISTRY];
    }
    // ...
  }
}
```

And inside every bundled app's `app.run()` (`src/runtime/cli.ts`):

```typescript
// src/runtime/cli.ts
async run(argv: string[] = process.argv.slice(2)): Promise<never> {
  const gateway = mcpGatewayRegistry();
  if (gateway) {
    // Imported by `argsbarg gateway`: hand over the MCP handler instead of parsing argv.
    gateway.register(this.gatewayApp(gateway.concurrent === true));
    return undefined as never;
  }
  // ... normal CLI parse & dispatch
}
```

Because each standalone plugin bundle has a top-level `await app.run()`, importing the bundle normally executes it. The `globalThis` hook hijacks `app.run()` during `await import(...)` so it hands over a low-level JSON-RPC `handle(req, writeResponse, controls)` callback instead of reading `process.argv` or starting stdio.

## What the next-major design currently says

Three places in the design docs touch this, and they currently leave the fate of `argsbarg gateway` ambiguous:

1. **[7.11 Startup commands and distribution](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#711-startup-commands-and-distribution):**

   > Agent-plugin manifests and `.mcpb` bundles supply a command and args for stdio, while gateway bundles need a defined loading contract.
   >
   > **Still to specify.** ... The gateway may keep loading new bundles in-process without accepting bundles from 8.x.

2. **[7.12 Breaking major without an 8.x migration path](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#712-breaking-major-without-an-8x-migration-path):**

   > **Decision.** No shims, legacy aliases, old-bundle support, migration tooling, or migration guide.

3. **[`docs/use-cases/child-apps.md`](../../../../docs/use-cases/child-apps.md):**

   > **Next-major preview.** The factory-based app model is selected, but the mount API below is illustrative. It doesn't run on 8.x; the 8.x MCP gateway combines stdio plugin bundles, not full app definitions.
   >
   > ```typescript
   > const suite = argsbarg({
   >   ...suiteMetadata,
   >   children: {
   >     billing: { app: billingApp },
   >     reporting: { app: reportsApp },
   >   },
   > });
   > ```

## Why this matters (the friction points)

The 8.x `mcpGatewayRegistry` trick has four real collisions with the v9 design:

1. **Top-level side effects on import.**
   In v9 ([7.1](./2026.11.18%20-%20Argsbarg%20next%20major%20design%20decisions.md#approach-c-use-a-surface-neutral-factory) and `child-apps.md`), library entries don't run on import, and standalone CLIs own their resources around `app.run()`:
   ```typescript
   // v9 standalone entry point
   const reports = createReportRepository(process.env);
   const app = buildApp(reports);
   try {
     await app.run();
   } finally {
     await reports.close(); // <-- BUG if `app.run()` returns immediately after registering!
   }
   ```
   Look at what happens if a v9 gateway imports that executable and hijacks `app.run()` the 8.x way: `app.run()` registers the handler and returns immediately, **so `finally { await reports.close(); }` closes the database before the gateway serves its very first MCP request!**

2. **Two different prefixing conventions.**
   - 8.x `argsbarg gateway` prefixes tools with a single underscore: `<alias>_<tool>` (`notes_read`).
   - v9 child mounts prefix tools with a double underscore: `<key>__<tool>` (`billing__list_invoices`) to avoid collisions when a key or tool contains `_`.

3. **Two different isolation / scoping models.**
   - 8.x `argsbarg gateway` shares one process env across all bundles (no prefix stripping, no per-bundle guards/auth boundary).
   - v9 child mounts scope `ctx.env` with `<KEY>_` / `<Key>-` prefixes and integrate CLI, REST, and MCP uniformly.

4. **Protocol & surface overlap.**
   - In 8.x, `argsbarg gateway` existed specifically because MCP was stdio-only and every plugin meant another Node process.
   - In v9, you already have **two** cleaner answers for most cases:
     - **Build-time composition (`children`)** when you control the suite repo (combines CLI, REST, and MCP in one executable).
     - **Shared Streamable HTTP (`/mcp`)** or a single long-lived suite daemon when multiple agent sessions connect to the same tools.

## The one case child mounts do NOT cover

Child mounts (`children: { billing: { app } }`) require writing and building a suite app in TypeScript.

They do **not** let an end user (or your own `~/.cursor/mcp.json` / `~/.claude.json`) point a CLI at three independently downloaded `.mjs` plugin bundles from three different repos (`obsidian.mjs`, `personal-log.mjs`, `gdocsmith.mjs`) and run them in one Node stdio process without creating a wrapper repo.

That single use case — **end-user runtime aggregation of independent pre-built stdio bundles** — is the only reason `argsbarg gateway` would still exist in v9.

## Concrete options for v9

| Dimension | Option A: Drop `argsbarg gateway` & `mcpGatewayRegistry` | Option B: Replace the `globalThis` hack with an explicit v9 bundle export |
| --- | --- | --- |
| Multi-app in one process (same owner/monorepo) | Use `children` mounts (CLI + REST + MCP) | Use `children` mounts |
| Combining 3rd-party `.mjs` bundles at runtime via `mcp.json` | Not built in (run separate stdio processes, or wrap in a tiny suite) | Supported via `argsbarg gateway` |
| `try { await app.run(); } finally { close(); }` safety | Safe — `app.run()` is never hijacked | Safe — bundles export an app/factory rather than running at import time |
| Cross-bundle argsbarg contract to maintain | None | Small explicit export contract (`export const app` or `export default`) + `2026-07-28` router |
| Complexity | Lowest | Moderate (must handle `2026-07-28` `server/discover`, `CacheableResult`, `tasks`, prefixing `<alias>__<tool>`, and cleanup on shutdown) |

### What Option B would look like (if kept)

Instead of hijacking `app.run()` via `globalThis[Symbol.for("argsbarg.mcp.gateway")]`, a v9 bundle built for both direct execution and gateway loading exports its app (or `createApp()`) and only calls `app.run()` when executed as the main module:

```typescript
// Standalone plugin bundle (v9, Option B)
export function createApp() {
  const store = createStore(process.env);
  const app = buildApp(store);
  return { app, close: () => store.close() };
}

// Only runs when launched directly (`node obsidian.mjs serve mcp --stdio`), NOT when imported by a gateway
if (import.meta.main) {
  const { app, close } = createApp();
  try {
    await app.run();
  } finally {
    await close();
  }
}
```

Then `argsbarg gateway` imports each bundle, calls `createApp()`, mounts them using the **same** child-mount composer (`children`), and calls every `close()` on shutdown — zero `globalThis` magic, zero duplicate MCP router code, and `finally { close(); }` never fires early.

## Decision

**Selected: Option A — drop `argsbarg gateway` and `mcpGatewayRegistry` completely in v9.** Multi-app executables use build-time `children` mounts ([`docs/use-cases/child-apps.md`](../../../../docs/use-cases/child-apps.md)), and standalone servers use explicit `{app} serve ...` launches without any `globalThis` `app.run()` interception.
